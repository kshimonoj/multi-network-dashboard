# 65: Coachタブの実装(壁打ち+クイズ、ヒント段階制御、エスカレーション、弱点記録、根拠リンク)

## 背景(64番からの引き継ぎ)

- 64番で調査・設計方針を確定済み(instructions/64_findings.md)。実装はまだ行っていない
- ソースは3つ、優先度は自社のナレッジ/調査履歴を最優先、ベンダーのベストプラクティスは補助:
  - Knowledge(承認済み、現在21件・今後も増える想定)
  - Network Investigation履歴(教材適格フィルタ: `!isError && answer>=400文字 && calls.length>0`、scheduled由来は教材価値が低いため除外・優先度を下げる)
  - Best Practice(29ルールのtitle/desc/references[])
- 「答えをそのまま返さず気づきを与える」ソクラテス式の応答は、**LLMに出し渋りの判断を委ねず、サーバ側でhintLevel(0→3)を管理**し、以下の3経路で必ず開示に到達させる設計:
  - 3ターン規則(同じ論点で3往復ヒントが続いたら開示レベルを上げる)
  - クイズ2往復(クイズモードでは2往復までヒント、以降は解説)
  - 障害対応中モード(後述のエスカレーション導線)
- 出典宣言・正誤判定は`[SRC:...]`/`[VERDICT:...]`のようなマーカー方式で行う(CLAUDE.mdの自然文パース禁止に準拠。自然文からの抽出に頼らない)
- UIトーンは既存タブ(teal基調)と差別化し、暖色系(amber、既存の`--accent-amber`を主色に）+丸みのあるチャットバブル+アイコンで親しみやすさを出す。文言はカジュアルなトーン
- ユーザー決定: デモ用途のため学習者IDによる識別・ログイン等の認証機構は不要。弱点データも誰でも見られる形でよい(限定公開・アクセス制御は不要)
- 位置付けは新規独立タブ「Coach」

## タスク

### Task 1: バックエンド基盤

1. `plugins/coach/`を新設し、以下を実装する:
   - hintLevel管理(0→3)のロジック(3ターン規則の判定を含む)
   - 3ソース(Knowledge/Network Investigation履歴/Best Practice)からの関連情報取得・優先順位付け(自社ナレッジ→調査履歴→ベストプラクティスの段階的フォールバック)
   - Coach用の関連度しきい値は、64番で実測していなかった値(0.20〜0.30のどこか)を実データで測定してから確定する。既存retrieve.tsの0.30という既定値が「サイト一致ボーナス0.20が乗る前提」だった点を踏まえ、サイト指定のないCoachでの適切な値を実際に試して決める
   - `[SRC:...]`/`[VERDICT:...]`マーカー方式のsystem prompt設計・パース処理
2. **重要な注意**: Knowledgeの`buildInjection()`を安易に呼ぶと`refCount`が汚染される(既存のナレッジ参照回数の指標定義が壊れる)。Coachが参照した際に`refCount`を加算しないよう、既存のKnowledge検索ロジックと分離するか、加算しないモードを設ける
3. 壁打ちの会話履歴の保持方式を実装する(セッション単位で構わない、64番の設計方針に従う)

### Task 2: エスカレーション導線

1. 壁打ち中に「もう答えを教えて」で直接回答(hintLevelを一気に最大にする、または即座に核心の回答を返す)に切り替えられるボタン/導線を実装する

### Task 3: 弱点の記録

1. つまずいた箇所(質問内容・ヒント要求回数等)を記録する仕組みを実装する(data/配下、既存プロジェクトの配置慣習に合わせる)
2. 学習者IDでの紐付けは不要(デモ用途のため)。記録は誰でも見られる形で表示する
3. 記録した弱点情報を、次回以降のクイズ出題やヒントの出し方にどう反映するかを実装する

### Task 4: 根拠へのリンク提示

1. 壁打ちの回答に、ヒントの元になったナレッジ・過去の調査結果・ベストプラクティスルールへのリンクを添える
2. **既存2タブへの小改修が必要**:
   - Knowledgeタブに、特定エントリへのdeep-link(highlight)機構を新設する(現状は存在しない。Best Practiceの`RuleReference.tsx`の`highlightRuleId` + `scrollIntoView`パターンを参考にしてよい)
   - Best Practiceタブは既存の`highlightRuleId`をCoachからのリンクで受け渡せるようにする

### Task 5: クイズ出題モード

1. 自社の過去事例(ナレッジ・調査履歴)からクイズを自動生成する(64番の設計方針に従う)
2. 出題→回答→フィードバックの流れを実装する(ここもマーカー方式で正誤判定を行い、2往復までヒント、以降は解説)
3. 同じ事例から繰り返し出題されないようにする(ナレッジの参照回数記録の仕組みを参考にしてよいが、Task 1の注意点通りrefCount自体は汚染しないこと)

### Task 6: UI実装

1. 新規独立タブ「Coach」を追加する
2. UIトーン: 暖色系(`--accent-amber`を主色)、丸みのあるチャットバブル、アイコンで親しみやすさを演出。既存タブのteal基調とは明確に差別化する
3. 壁打ちチャット画面とクイズモードの切替を実装する
4. エスカレーションボタン、弱点記録の表示、根拠リンクの表示を画面に組み込む
5. i18n対応(ja.json/en.json)。カジュアルなトーンの文言にする

### Task 7: 動作確認・本番反映

1. 実際に壁打ちを行い、3ターン規則でhintLevelが上がること、エスカレーションボタンで直接回答に切り替わることを確認する
2. クイズモードで出題→回答→フィードバックの流れを確認する
3. 弱点記録が実際に蓄積され、表示されることを確認する
4. Knowledgeタブ・Best Practiceタブへのdeep-linkが正しく機能することを確認する(遷移先でハイライト・スクロールされるか)
5. Coachの参照によってKnowledgeの既存`refCount`が変化していないことを確認する(Task 1の注意点の検証)
6. 日英切替・ダーク/ライトモードでの表示崩れが無いことを確認する
7. 標準運用ルール通り、本番Dockerコンテナのrebuild(`docker compose up -d --build`)まで行い、本番ポート(8092)での動作確認まで実施する

## 制約

- Central/Mistの設定変更は一切行わない
- git操作は行わない(コミット等は別途指示があるまで実施しない)
- 認証・学習者ID機構は実装しない(デモ用途のため不要という決定を守る)
