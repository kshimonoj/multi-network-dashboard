# 12: Central Event調査 + クライアント一覧 + クライアント詳細(オプション) + ポーリング間隔設定化

## タスク

### Task 1: Central Event情報の取得可否調査

1. 以下2つを実際に(既存の.env資格情報で)試す:
   - https://developer.arubanetworks.com/new-central/reference/eventlistv1 の仕様に沿ったエンドポイント呼び出し
   - `https://internal.api.central.arubanetworks.com/network-troubleshooting/v1/events`
2. 2つ目のホスト名(`internal.api.central.arubanetworks.com`)は通常の開発者向けAPIホストと異なり、内部限定である可能性がある。認証エラー(401/403)やアクセス拒否になった場合は、それ以上回避しようとせず「アクセス不可」として結果を記録すること。無理な回避策(別ホスト名の推測試行等)は行わないこと
3. 取得できた場合、11番で確認済みの他の情報(Alert等)と同様にサイト単位でフィルタして返せる形式か確認する
4. 調査結果(成功した場合のレスポンス形式、失敗した場合のステータスコード・エラー内容)を`instructions/12_findings.md`に記録する
5. 取得できた場合は、11番で実装した詳細パネルのEventセクション(現状Central側は「取得不可」表示)に反映する

### Task 2: 接続クライアント一覧の拡充

1. 11番の詳細パネルにあるクライアント情報セクションを、件数表示だけでなく**実際の個々のクライアントの一覧**(MACアドレス、ホスト名/デバイス種別、接続SSID、帯域(2.4GHz/5GHz/6GHz)、接続AP、信号強度等、Central/Mistそれぞれの`clients`系APIで取得できる範囲)に拡充する
2. クライアント数が多いサイトでも一覧が見やすいよう、テーブル形式・スクロール可能な表示にする
3. Central/Mistで取得できる項目に差がある場合は、無理に統一せず取得できる項目のみ表示する(欠損は「—」等で表現)

### Task 3: クライアント詳細情報(オプション、条件付き実装)

1. クライアント一覧の各行をクリックした際に、より詳細な情報(接続履歴、通信品質、過去のローミング等、Central/Mistでそれぞれ取得可能なもの)を表示する機能を検討する
2. 実装するかどうかは以下の基準で判断する:
   - クライアント詳細を取得するAPI呼び出しが、クライアント一覧の表示に対して**追加で何回必要か**(1クライアントあたり1回程度であればオンデマンドで許容範囲、多数の追加呼び出しが必要であれば見送る)
   - 実装の複雑さが11番のサイト詳細パネルと同程度で収まるか
3. 実装を見送る場合は、その理由(必要API呼び出し数、複雑さ等)を完了報告に明記し、コードは変更しない
4. 実装する場合も、11番と同様にオンデマンド取得(クリックされた時のみ)とし、定期ポーリングには含めない

### Task 4: ポーリング間隔のデフォルト変更と設定可能化

1. Global Overviewの定期ポーリング間隔のデフォルトを、現状の3分から**5分**に変更する
2. ポーリング間隔をユーザーが変更できるようにする。実装方法は以下のいずれかで構わない(実装側の判断でよい):
   - Global Overview画面に間隔選択のUI(例: 1分/3分/5分/10分/15分等のプルダウン)を追加し、サーバー側に保存して`poller.ts`が動的に反映する
3. 変更可能な範囲には妥当な下限(例: 1分未満は選択不可)を設け、レート制限を圧迫しない範囲に収める
4. 設定変更後、実際にその間隔でポーリングが行われることを確認する
5. 設定値はコンテナ再作成後も保持されるようにする(ファイルへの永続化等)

## 完了報告

verified-report形式で報告すること。特に:

- Central Event APIの調査結果(取得できたか、できなかった場合の理由)
- クライアント一覧の実データでの表示確認結果(Central/Mist双方)
- クライアント詳細を実装したか見送ったか、その判断根拠
- ポーリング間隔のデフォルト変更・設定変更UIの動作確認結果
- `docker compose up -d --build`後の反映確認結果

git操作は行わないこと。
