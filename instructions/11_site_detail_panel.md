# 11: サイト別詳細情報(Health/SLE・クライアント・デバイス・Alert/Event/Insight)の追加(multi-network-dashboard)

## 前提・方針(確定事項)

- 追加先はGlobal Overview(直接APIダッシュボード)。MCP調査ページ(Insight Agent)側は対象外
- 見せ方は、サイト一覧テーブルの行をクリックして開く**詳細パネル/モーダル**。一覧テーブル自体の列は増やさない
- レート制限対策として、この詳細情報は**サイト一覧の常時ポーリング(3分毎)には含めず、詳細パネルを開いた時だけオンデマンドで取得する**。22サイト分を毎回取得するような設計にはしないこと

## タスク

### Task 1: 利用可能なAPIの調査

Central・Mistそれぞれについて、以下の情報をサイト単位/デバイス単位で取得できるAPIエンドポイントを調査する:

1. サイトのHealth/SLEスコア(Central: サイトヘルス関連API。Mist: `get_mist_insights`系だが08/09番で判明した通り`query_type`等の必須パラメータがあるため、正しいパラメータの組み合わせを確認する)
2. クライアント情報(接続中クライアントの一覧: MACアドレス、接続SSID/デバイス、シグナル強度等、取得できる範囲でよい)
3. デバイス個別のステータス(現状のbulk取得は台数集計のみのため、個々のAP/Switch/Gatewayのシリアル番号・モデル・稼働時間・個別の状態を取得できるAPIを確認する)
4. Alert/Event/Insight情報(現状は件数のみ取得しているアラートについて、個別の詳細(発生時刻、対象デバイス、内容、重要度等)を取得できるAPIを確認する。Eventについても同様に確認する)
5. それぞれのAPI呼び出しがレート制限にどう影響するか(1回のサイト詳細表示で何回のHTTP呼び出しが必要になるか)を記録する
6. 調査結果を`instructions/11_findings.md`に記録する

### Task 2: バックエンドAPI設計・実装

1. `GET /api/global-overview/sites/:siteId/detail`(またはそれに類するエンドポイント)を新設し、Task 1で確認した各情報をオンデマンドで取得して返す
2. このエンドポイントは3分毎の定期ポーリング(`poller.ts`)には組み込まない。詳細パネルを開いた時のみ呼ばれるようにする
3. 取得に失敗した項目(例: Mistの健全性スコアがそもそも取得できない等、05/06番で判明した既知の欠損)は、既存の方針(nullは「—」表示)を踏襲し、エラーと欠損を区別する
4. 同一サイトを短時間に連続して開いた場合の呼び出し過多を防ぐため、軽い最短間隔ガードまたは短時間キャッシュ(例: 30秒程度)を設ける

### Task 3: フロントエンドの詳細パネル/モーダル実装

1. サイト一覧テーブルの行クリックで開く詳細パネル(モーダルまたはスライドインパネル)を実装する
2. 以下のセクションで構成する(タブ切り替え、またはスクロールする1画面のどちらでも実装側の判断でよい):
   - Health/SLEスコア
   - 接続クライアント一覧
   - デバイス個別ステータス一覧(AP/Switch/Gatewayそれぞれ)
   - Alert/Event/Insight一覧
3. 既存の地図(SiteMap.tsx)からサイトピンをクリックした場合も、同じ詳細パネルが開くようにする(テーブル行クリックと地図ピンクリックの両方から同じ詳細に到達できるようにする)
4. ダークモード両テーマでの表示を確認する
5. データ取得中はローディング表示、取得失敗時は既存の共通エラー表示パターン(08/09番で実装した表示)に準じた表示にする

### Task 4: 動作確認

1. 複数のサイト(Central側・Mist側それぞれ)で詳細パネルを開き、各セクションが実データで正しく表示されることを確認する
2. 詳細パネルを開いてもGlobal Overview全体の定期ポーリング頻度が変化しないこと、詳細パネルのAPI呼び出しがレート制限を圧迫しないことを確認する
3. `docker compose up -d --build`で反映し、`/health`と実画面を確認する

## 完了報告

verified-report形式で報告すること。特に:

- Task 1で判明した各情報の取得可否(取得できないものがあれば理由も)
- 詳細パネルの実データでの表示確認結果(Central/Mist双方)
- レート制限への影響(1サイトあたりの追加HTTP呼び出し回数、常時ポーリングに影響がないこと)
- `docker compose up -d --build`後の反映確認結果

git操作は行わないこと。
