# 41: 日次レポート生成基盤(データ収集・保存・LLM分析・スケジュール)

## 前提・確定事項

- このタスクではUI(レポートタブの画面)は作らない。**日次レポートを生成し、ファイルとして蓄積する仕組みだけ**を対象とする(画面は42番)
- 週次/月次レポートは、生データへの再クエリではなく**蓄積済みの日次レポートを集計する方式**にする(この方式自体は43番で実装するが、今回のデータ構造はその集計に耐えられる形で設計すること)
- 過去に遡ったトレンドは無い(Global Overviewが最新スナップショットしか保持していないため)。このタスクの実行以降、日次スナップショットを蓄積し始める前提でよい
- 生成タイミング: 既定は毎日9:00(設定変更可能)。MacBookがダウンしていて実行できなかった場合は、起動後しばらくしてから後追いで生成する
- 保持期間: 既定は無期限保持。ただし設定で上限(例: 保持日数)を指定できるようにする(Webhookログ/Streamingの既存Retention設定パターンを踏襲)

## タスク

### Task 1: 日次データ収集の設計・実装

1. 以下のデータソースから、その日(前日分、9:00に実行するので対象は「前日0:00〜24:00」)の情報を集約する仕組みを作る:
   - **Global Overview**: 各サイトのCentral健全性スコア・Mist SLE総合スコア(サイトごとの値。当日の平均を計算するために、実行時点のスナップショットを使うか、当日複数時点の値を後で平均できるよう記録するか、実装しやすい方でよい。既存のポーリング機構(5分間隔)から当日分のデータが得られるならそれを使う)、接続端末数、トラフィック量(取得可能なAPIがあるか確認し、無ければ取得できるものだけ記録する)
   - **Webhookログ**: 当日分の全イベント/アラート(New Central/Classic Central/Mist/GLP)。件数集計(重要度別)と、個別の重大アラート(デバイス名・発生時刻・内容)
   - **Streaming(Central)のAudit Trail**: 当日分の設定変更等のイベント
   - **ネットワーク調査の実行履歴**: 当日実行された調査(手動・自動問わず)のクエリと対象サイト/デバイス(同じ問題が繰り返し調べられていないかの手がかりとして使う)
2. 各データソースの当日分取得ロジックを実装する。既存の各機能(Global Overview、Webhookログ、Streaming、ネットワーク調査)のデータ取得・保存の仕組みを流用してよい(新たにAPIを叩き直す必要はなく、既存のポーリング・保存済みデータから当日分を抽出する形で構わない)

### Task 2: LLMによる分析(起きたこと・問題の抽出)

1. Task 1で集約した当日分の生データを、Insight Agentに渡して以下を生成させる:
   - **「この期間に起きたこと」**: 対象機器・発生日時・内容が分かる形の箇条書き(3〜8件程度、重要度の高いものを優先)
   - **「検出された問題」**: 表形式で使えるデータ構造(問題名・対象機器・初回発生日時・プラットフォーム・重要度・再発性・根本原因・影響範囲・次のアクション)。再発性は、当日以前の同種の問題(過去の日次レポートやWebhookログの履歴)と照合して判断させる
2. このLLM呼び出しは、既存の自動事前調査(enrich.ts)のパターンを参考にしつつ、個別アラート単位ではなく「1日分のデータ全体」を渡す形の新しいプロンプト設計にする
3. 生成結果を含めて、日次レポートのデータ構造(JSON)を確定し、`data/reports/daily/YYYY-MM-DD.json`のような形で保存する

### Task 3: スケジュールと後追い取得

1. 既定で毎日9:00に前日分のレポートを生成するスケジュールを実装する(既存のnode-cron等の仕組みを踏襲)
2. 生成時刻は設定で変更できるようにする
3. 起動時(コンテナ起動・アプリ起動時)に、直近で生成されるべきだった日次レポートが欠けていないか確認し、欠けていれば後追いで生成する処理を実装する(例: 過去7日分をチェックし、無ければ生成する、程度の範囲でよい)

### Task 4: 保持期間の設定

1. 日次レポートの保持期間設定(既定: 無期限、設定で日数を指定可能)を実装する
2. 設定に応じて古い日次レポートファイルを削除する処理を実装する

### Task 5: 動作確認

1. 実際に日次レポート生成を手動トリガーできるAPI(例: `POST /api/reports/daily/generate?date=YYYY-MM-DD`)を用意し、実データで生成を確認する
2. 生成された`data/reports/daily/*.json`の中身(起きたこと・問題一覧が実データに基づいた妥当な内容になっているか)を確認する
3. スケジュール実行(9:00)が正しく登録されることを確認する(実際に9:00まで待つ必要はなく、設定・登録されていることの確認でよい)
4. 起動時の後追い取得ロジックを、意図的に日次レポートが無い状態を作って動作確認する
5. 保持期間設定に応じた削除処理が動作することを確認する
6. `docker compose up -d --build`で反映し、既存の他機能に影響が無いことを確認する

## 完了報告

verified-report形式で報告すること。特に:

- 各データソースから当日分をどう抽出したか(既存の仕組みの流用範囲)
- 接続端末数・トラフィック量が実際に取得できたか(できなかった場合は理由)
- LLM分析で生成された「起きたこと」「問題」の実データサンプル
- スケジュール・後追い取得・保持期間設定それぞれの動作確認結果
- `docker compose up -d --build`後の反映確認結果、既存機能への影響が無いことの確認

git操作は行わないこと。
