## 1. Task 1: ソースの整理・設計

### 1-1. ナレッジ(承認済み知見)

スキーマは `plugins/knowledge/types.ts` の `KnowledgeEntry`(23 フィールド)。実データ(`data/knowledge/entries.json`)の実測:

| | 値 |
|---|---|
| 全件 | 76 |
| 内訳 | pending 66 / approved **8** / merged 1 / rejected 1 |
| 承認済みの scope | general 7 / site 1 |
| 承認済みの platform | mist 6 / central 2 |
| 承認済みの lang | ja 7 / en 1 |
| タグ数 | 1 件あたり 4〜8 個 |
| 出典数 | 1 件あたり 1〜2 件 |
| `refCount` の分布 | 31, 23, 23, 10, 6, 4, 1, 0 |

**(a) Coach が使えるフィールド**

| フィールド | Coach での用途 |
|---|---|
| `title` / `symptom` | **出題文・壁打ちの導入に使う「見せてよい部分」** |
| `rootCause` / `action` | **答え。ソクラテス式では隠す部分**。開示は hintLevel=3 でのみ |
| `tags` | 話題キー。弱点記録の軸・クイズの分類・関連度計算の入力(§5-2) |
| `scope` / `site` / `device` / `platform` | 難易度と適用範囲の判定。`scope="site"` は「自社ならでは」の最も強いシグナル |
| `sources[].runId` | 元調査へのリンク(§5-3)。既存の `onOpenHistoryFocus(runId)` にそのまま渡せる |
| `approvedAt` / `edited` | 人が目を通した時刻。教材としての信頼度 |
| `refCount` / `lastReferencedAt` | **読むだけ**(重要度の代理指標)。**書かない**(下記 (d)) |

**(b) `symptom → rootCause → action` の 3 段構成が、そのままソクラテス式の 3 段になる。**
これはナレッジ設計(46 番)の副産物だが、Coach にとっては決定的に都合が良い。
「症状を見せる → 原因を考えさせる → 対処を考えさせる」が、追加の教材加工なしで成立する。

**(c) 承認済みだけを使う。** pending 66 件は人の目を通していない。
調査で誤った前提を注入するより、教育で誤った知識を教える方が害が長く残る(junior はそれを疑えない)。

**(d) `refCount` を Coach が加算してはいけない(重要)**
`refCount` の定義は「**調査プロンプトに注入された回数**」で、`retrieve.ts` 冒頭と `store.ts:258-284` に
「参照 = 注入で定義する」と明記されている(自然文パースを避けるための 47 番の設計判断)。
Coach が同じカウンタを回すと「そのナレッジが調査で役に立ったか」の指標が壊れる。
→ Coach は `buildInjection()`(内部で `recordReferences()` を呼ぶ)を**使わない**。
  `relevantEntries()` + `buildSection()` を直接呼ぶ(どちらも export 済み。`previewMatches()` も副作用なし)。
  Coach 側の利用実績は §3-3 の別ファイルに持つ。

**(e) 言語**
承認済み 8 件のうち 1 件が `lang:"en"`。本文は「実行時の記録」なので翻訳しない(CLAUDE.md)。
→ Coach の地の文(ヒント・問いかけ)は UI 言語、**引用する素材は原文のまま**。
  ナレッジタブが既に同じ扱い(`LangNote` コンポーネントがある)なので、表示の作法もそれに倣う。

### 1-2. 調査履歴(Network Investigation)

**保存場所と形式**: `data/network-investigation/query-history.jsonl`。追記専用の JSON Lines。
型は `plugins/network-investigation/api.ts:243` の `QueryHistoryRecord`。

実測(2026-07-23 〜 2026-08-07、**215 件 / 748KB**):

| 項目 | 実測 |
|---|---|
| `source` | manual 116 / auto 75 / scheduled 24 |
| `isError:true` | 10 |
| セッション数 | 190(うち複数ターンのセッションは 15) |
| `suggestedActions` あり | 188 |
| `knowledgeRefs` あり | 54(= 47 番の注入が効いている実績) |
| 回答本文の長さ | 中央値およそ 800〜900 文字、最長 1,500 文字弱 |

**(a) 教材適格の実測フィルタ**

`!isError && answer.length >= 400 && calls.length > 0` を当てると **176 件**。内訳:

| source | 件数 | distinct なクエリ文 | 教材価値 |
|---|---:|---:|---|
| manual | 79 | 60 | **最も高い**。人が実際に困って投げた問い |
| auto | 73 | 70 | **高い**。実アラート起点で、自社で実際に起きた事象 |
| scheduled | 24 | **2** | **低い**。定点観測なので同じ問いの反復 |

→ **scheduled は既定で教材プールから外す。** 残り **152 件**が実質のプール。
(46 番でナレッジ抽出が scheduled を既定除外しているのと同じ理由で、同じ判断になる。)

**(b) `calls[]` が最大の資産(重要)**

`HistoryToolCall`(`api.ts:227`)は 1 回の調査で呼んだ MCP ツールを **順番どおり**に持っている:
`server` / `platform` / `tool` / `status` / `detail`(引数の要約)/ `count`(結果件数)/ `error` / `input`。

ナレッジが持つのは**結論**だけ。`calls[]` が持つのは**そこに至る道筋**で、
「概況ツールから入って、どこで絞り込んで、どのツールで裏を取ったか」がそのまま残っている。
junior に最も欠けているのは結論の知識ではなく**切り分けの順番**なので、
**手順を教える教材はここにしか無い。** これが Coach を「一般的な LLM 家庭教師」と分ける唯一の要素になる。

クイズ形式 2(§3-1)はこれを直接使う設計にする。

**(c) 履歴には検索機構が無い**
`GET /history`(全件を新しい順)と `GET /history/session/:sessionId` だけで、本文検索の口が無い。
→ Coach 側で素材検索を実装する必要がある。`plugins/knowledge/similarity.ts` の
  `bigrams()` / `normalizeText()` は export されているので、同じ軽量手法を再利用する
  (埋め込み検索・ベクトル DB は 47 番で不採用と決まっており、ここでも踏襲する)。

**(d) レポート(日次/週次/月次)との関係**

`data/reports/daily/YYYY-MM-DD.json` の構造を確認した。調査に関わる部分は:

```
data.investigations = { total, bySource, errors, items[](最大 5), truncated, repeated[] }
analysis            = { status, summary, highlights[], issues[] }
```

- `items[]` は**その日の調査の抜粋**であって、履歴の別コピーではない。原本は常に jsonl 側。
- **`repeated[]` が有用**: 「同じ事象が繰り返し起きている」= その会社ならではの構造的な問題を指す。
- `analysis.issues[]` / `highlights[]` は LLM が書いた**その日の所見**で、教材本文としては薄い
  (日付に強く紐づき、後から読んでも文脈が復元できない)。

→ **レポートは教材本文としては使わない。素材の「重み付けシグナル」としてだけ使う。**
  `repeated[]` に現れる事象を元にした調査を、クイズ・壁打ちの素材として優先する。
  これで「その会社ならではの事象」を機械的に浮かび上がらせられる。

**(e) 実データの扱い**
履歴の `answer` にはサイト名・機器名などが素のまま入る。社内の junior 向けなので画面表示は
調査タブと同じ扱いでよいが、**Coach には共有テキスト・印刷レイアウト機能を作らない**
(調査タブの `shareText.ts` / `printClone.ts` 相当は移植しない)。教育用途に外部共有の必然性が無く、
55 番・61 番で実データ混入の実績があるため、経路そのものを作らないのが安い。

### 1-3. ベストプラクティスのルール(29 ID)

`plugins/best-practice/rules.ts`。SEC-01〜13 + RF-01〜16 = **29 ID**(mechanical 25 / llm 4)。
1 件あたりのフィールド: `id` / `category` / `platform` / `target` / `severity` / `method` /
`references[]`(タイトル + URL)/ `sources[]` / `enabledByDefault` / `titleKey` / `descriptionKey`。

**(a) 教材向きかの評価**

| | 評価 |
|---|---|
| `title` / `desc` | **辞書(`bestPractice.rules.<ID>.title/desc`)にあり、ja/en 両方が揃っている。** ナレッジ本文と違い翻訳済みなので、どちらの言語でも素材として使える。ただし 1〜2 行と短く、**単体では教材として薄い** |
| `references[]` | **教材として最も価値が高い部分。** ベンダー公式ドキュメントのタイトル + URL。「宿題として読ませる」対象になる。翻訳しない規定(49 §4-4)がそのまま活きる |
| `severity`(must/strong/recommended/advisory) | 難易度と優先度の自然な順序。「まず must から覚える」が作れる |
| `category`(security/rf) | 話題の大分類。弱点タグの上位カテゴリに使える |
| `sources[]` | どのコマンド / API で確かめられるか = **「どこを見れば分かるか」の教材**。地味だが junior には有用 |

**(b) 診断結果(runs)は使わない**
`data/best-practice/runs/` の診断結果は「今この顧客の設定がどうなっているか」で、
使うと Coach が監査ツールになる。指示にも「診断結果そのものではなく」と明記されている。
Coach が読むのは `GET /api/best-practice/rules`(カタログ)だけ。

**(c) `requiresLegalReview`(SEC-10 / SEC-11)の扱い**
封じ込め系は 49 §3-5 で「無効を fail にしない / 法務・セキュリティ部門の承認を促す向きに統一」と
決まっている。Coach でも同じ立場を取り、**「有効にすべき」と教えない**。
「有効にするなら誰の承認が要るか」を考えさせる問いにする。教育コンテンツは現場の行動を直接変えるので、
ここを崩すと 49 番の判断が実質的に無効化する。

**(d) 位置づけ**
ルールは「一般論の層」であると同時に、**話題の語彙**として全層で使う。
壁打ちの内容が SEC-06 の話なのか RF-03 の話なのかを紐づけておくと、
弱点記録(§5-2)とクイズ選択(§3-1)の軸がナレッジのタグと繋がる。

### 1-4. 3 層の担当の違い(役割分担)

| | 何を持っているか | 教えられること |
|---|---|---|
| ナレッジ(承認済み) | 症状 → 原因 → 対処。人が承認済み | **結論**。「この症状ならここを疑う」 |
| 調査履歴 | クエリ・回答本文・**呼んだツールの順番**(`calls[]`) | **手順**。「どう切り分けたか」 |
| ベストプラクティス | ルール名・説明・重大度・**公式ドキュメント URL** | **語彙と一般論**。「そもそも何が推奨なのか」 |

3 つは代替関係ではない。**同じ話題について 3 層すべてが揃うのが理想形**で、
その場合 Coach は「うちで実際に起きたこの事例(ナレッジ)を、この順番で切り分けて(履歴)、
ちなみに一般論としてはこう推奨されている(ルール)」という三段重ねの教材を作れる。

### 1-5. 優先順位付けロジックの設計方針

**基本構造: 段階的フォールバック + 層の明示**

```
入力: junior の質問文(+ 直前までの壁打ち文脈から抽出したキーワード)
  │
  ├─ Layer A: 承認済みナレッジ  ── 該当あり ──▶ 主素材にする  [自社の知見]
  │      relevance() >= 0.30 の上位 3 件
  │
  ├─ Layer B: 調査履歴          ── 該当あり ──▶ 主素材にする  [自社の記録]
  │      bigram 重なり係数 >= しきい値 の上位 3 件(scheduled 除外・isError 除外)
  │
  └─ Layer C: ベストプラクティス ─────────────▶ 補助のみ      [一般論]
         タグ / カテゴリのキーワード一致
```

**(a) 層の選択はコードで行い、LLM に選ばせない。**
47 番と同じ設計にする。LLM に 3 層すべてを渡して「適切なものを選べ」と指示すると、
何を根拠にしたかが自然文でしか分からなくなり、CLAUDE.md の禁止事項(自然文パース)に触れる。
コードが素材を確定してからプロンプトに載せる。

**(b) A と B は排他ではない。両方当たれば両方載せる。**
「結論(A)」と「手順(B)」は担当が違うので、揃うほど教材として良くなる。
上限は合計 5 件程度(コンテキストと、junior が一度に扱える情報量の両方の制約)。

**(c) Layer C は単独で主素材にはしない。**
C だけが当たった場合は、回答の冒頭で
**「これはうちの記録には無い話なので、一般的な推奨から説明するね」**と明示する
(この文言は辞書に日英で置く。サーバ側で文章を組み立てない — CLAUDE.md の「サーバ生成の文言」項)。
自社の事実と一般論を混ぜて話すのが、この機能で最もやってはいけないこと。
junior は区別できないまま「うちではこうなっている」と覚えてしまう。

**(d) 「その会社ならでは」の強度スコア**

同じ層の中での並べ替えは、以下の加点で行う(すべてコードで計算できる値):

| シグナル | 加点の意図 |
|---|---|
| ナレッジの `scope === "site"` / `device` | 特定の環境に紐づく = 自社固有性が最も高い |
| レポートの `repeated[]` に現れる事象 | 繰り返し起きている = 構造的な自社の問題 |
| `source === "auto"`(実アラート起点) | 実際に鳴った事象。作り物でない |
| 承認済みナレッジの元調査でもある履歴 | A と B が同じ事象を指す = 重要度が高い(ただし**重複表示はしない**。A 側にまとめて B はリンクだけ) |
| `refCount` が高いナレッジ | 調査で繰り返し役立った = 現場で効く知見(読むだけ。§1-1(d)) |

**(e) しきい値について(実装時に測る前提)**

`retrieve.ts` の既定は 0.30。同ファイルの冒頭に「0.2 まで下げると同サイトの無関係な知見が
ぶら下がり始める」という実測に基づく記載がある。ただしこれは**サイト一致ボーナス 0.20 が乗る前提**で、
**Coach は原則サイトを指定しない**(junior は「どのサイトか」から分かっていないことが多い)ため、
その加点が発火しない。よって Coach では 0.2 台まで下げられる可能性がある。
→ **これは仮説。実装時に実データで測って決める。** 現時点では既定 0.30 で始め、
  0.20〜0.30 の帯を「関連事例(副次リンクのみ、本文には載せない)」として扱う案を第一候補とする。

## 2. Task 2: ソクラテス式応答の設計

### 2-1. system prompt の設計方針

**(a) Insight Agent との対比(まったく別物として設計する)**

| | Insight Agent(既存) | Coach(新設) |
|---|---|---|
| 目的 | 即答・診断 | 気づき・定着 |
| 事実の出どころ | **MCP のライブ結果のみ** | **過去の記録のみ**(プロンプト内で完結) |
| MCP | 必須 | **使わない** |
| 出力量 | 箇条書き中心 5 行 | 5 行程度 + **問いかけ 1 つで終える** |
| 結論 | 最初に出す | **隠す**(hintLevel で段階開示) |
| 相手 | 分かっている人 | 分かっていない人 |

**(b) Coach は MCP を繋がない(重要な設計判断)**

理由 3 つ:
1. **役割の分離**。「今うちの AP はどうなってる?」は Coach の仕事ではない。調査タブへ誘導する(§5-1)。
   Coach が現在の状態を語れるようにすると、junior は調査タブを覚えなくなる。
2. **速度**。実測した履歴 1 件の `durationMs` は **113,636ms(約 113 秒)**。対話にこの待ちは成立しない。
   MCP なしなら knowledge/extract.ts・best-practice/llm.ts と同じ軽量呼び出しになる。
3. **教材の再現性**。同じ素材からは同じ教え方が出る方がよい。ライブデータが混ざると
   「昨日と今日で言うことが違うコーチ」になる。

実装形態は既存の 2 例(`plugins/knowledge/extract.ts:192` / `plugins/best-practice/llm.ts`)と同じ
`claude --print --strict-mcp-config --mcp-config '{"mcpServers":{}}' --disallowedTools ... --append-system-prompt`。
このパターンは 2 プラグインで実績があるので、そのまま踏襲する。

**(c) system prompt の骨格(ja / en 両方を用意する。CLAUDE.md 必須)**

```
1. 役割
   あなたはネットワーク運用チームの先輩。答えを教える人ではなく、気づかせる人。

2. 絶対規則
   - 与えられた教材に無い事実を作らない(extract.ts と同じ縛り)
   - 現在のネットワークの状態は語らない。聞かれたら「調査タブで見てみよう」と促す
   - hintLevel が 3 未満のあいだ、原因と対処を直接言わない
   - 1 ターンにつき問い返しは 1 つだけ(複数問うと初学者は固まる)
   - 相手を試さない。間違いには「違う」ではなく「そう考えた理由は?」で返す
   - 専門用語は正しいまま使い、短い言い換えを添える(用語を崩すと現場で通じなくなる)

3. 手順(1 ターンの型)
   ① 相手の理解の現在地を 1 つだけ確認する
   ② hintLevel に応じたヒントを 1 つ出す
   ③ 相手に考えさせる問いで終える

4. 出力マーカー(半角のまま。翻訳・全角化を禁止)
   [SRC:knowledge:<id>] / [SRC:history:<runId>] / [SRC:rule:<RULE-ID>]
   [LEVEL:L1|L2|L3]

5. 分量: 5 行程度
```

`hintLevel` と `level` は**プロンプトに値として渡す**(モデルに決めさせない)。
マーカーの扱いは `insight-agent.ts` の `detectPlatformJudgments()` / `stripPlatformJudgments()` と同型で、
**検出は内部判定にだけ使い、ユーザーに見せる本文からは必ず取り除く**(CLAUDE.md)。

### 2-2. 質問レベルに応じたヒントの出し方

**(a) レベルは自己申告させない。** junior は自分のレベルを判定できない
(「何が分かっていないか」が分かっていないのが初学者の定義に近い)。

**(b) 3 段階モデル**

| | 状態 | ヒントの出し方 |
|---|---|---|
| **L1** | 用語が分からない | 用語の意味 + **どの画面のどこを見るか**。まず「見る場所」を教える |
| **L2** | 用語は分かるが切り分けの順番が分からない | **順番を問う**。「まず何から確かめる?」「その結果が○○だったら次は?」 |
| **L3** | 手順は踏めるが原因の絞り込みができない | **対立仮説を突きつける**。「その仮説だと説明できない事実が 1 つある。どれ?」 |

**(c) 判定に使う信号(すべてコードで観測できる値)**

- 質問文に技術用語がいくつ含まれるか(小さなキーワード辞書との照合)
- 質問文の長さ・具体性(機器名・時間帯・症状の有無)
- セッション内のターン数、直前の Coach の問いに答えたか / 新しい質問を投げたか
- 保存済みの弱点プロファイル(§5-2)のそのタグでの実績

※ これは**ユーザーの入力**を機械的に見るだけで、CLAUDE.md が禁じる「**モデル出力**の自然文パース」には当たらない。
  モデル側の見立ては `[LEVEL:L2]` マーカーで受け取り、次ターンの入力に反映する。

**(d) L1 には選択肢を出す。** 白紙の入力欄は初学者を固まらせる。
壁打ちでも、L1 と判定した相手には「こういう聞き方もできるよ」の例を 2〜3 個チップで出す
(調査タブの `SuggestedActions.tsx` と同じ UI パターンが流用できる)。

### 2-3. 出し渋りを防ぐバランス設計(この機能で最も重要)

**「いつ答えを出すか」をモデルに判断させないのが設計の核心。**
モデル任せにすると、プロンプトの言い回しやモデル更新で無言に挙動が変わり、
しかも「出し渋りすぎている」ことは画面から見えない。サーバが状態機械として持つ。

**(a) hintLevel(サーバが保持し、決定的に進める)**

| level | Coach が出すもの |
|---:|---|
| 0 | 問い返しのみ。「今どこまで確かめた?」 |
| 1 | 見るべき**観点を 1 つ**。「電波側と有線側、どっちの話だと思う?」 |
| 2 | **絞り込みの範囲**を提示。「有線側だとしたら、確かめる場所は 3 つある。1 つ挙げてみて」 |
| 3 | **答えを開示** + なぜそうなるかの筋道 |

**(b) 3 ターン規則**
同じ論点で 3 往復して核心に近づかない場合、次のターンで**必ず** hintLevel=3 にする。
根拠: 生産的な苦戦(productive struggle)には有限の閾値があり、
成功体験のない反復は「自分には無理だ」の学習になる。実運用で調整できるよう設定値(既定 3、範囲 2〜5)にする。

**(c) 明示エスカレーション** — 「もう答えを教えて」でいつでも hintLevel=3(§5-1)。

**(d) 障害対応中モード**
セッション開始時に「今、障害対応中?」をワンクリックで選べる。Yes なら**最初から hintLevel=3**。
Coach はまず即答し、そのあとに「今回のポイント」を **1 行だけ**添える。
これがユーザーの言う「実際の障害対応中にヒントで粘りすぎることの危険性」への構造的な答えで、
エスカレーションボタンを押させる(= 押す判断を junior に負わせる)より安全。

**(e) 開示したターンで学習を閉じない**
hintLevel=3 のターンの末尾に、必ず 1 問だけ残す:
「次に同じ症状を見たら、最初にどこを見る?」
答えを聞いた直後に自分の言葉で言い直させる(retrieval practice)。**これがあるかないかで定着が変わる。**

**(f) 出し渋りの可視化**
hintLevel が上がらないままターン数だけ伸びたセッションを記録し、Coach の設定画面に出す。
「粘りすぎ」を運用で気付けるようにする(モデルの挙動は静かに変わるので、指標がないと分からない)。

### 2-4. 会話履歴の保持方針

**セッションと学習者プロファイルを、別のものとして分けて持つ。**

| | 置き場 | 形式 | 理由 |
|---|---|---|---|
| 壁打ちセッション(本文) | `data/coach/sessions.jsonl` | 追記専用 JSONL | 調査履歴と同じ形にしておくと相互リンクが素直。`sessionId` は調査タブと同じく **view が採番してサーバが受け取る**方式(`api.ts:243` の設計を踏襲) |
| 学習者プロファイル | `data/coach/learners.json` | 1 ファイル JSON | 数十件想定で常に全件を横断して読む。`knowledge/entries.json`・`tagged-targets/tags.json` と同じ判断 |
| 素材の利用実績 | `data/coach/material-usage.json` | 1 ファイル JSON | §3-3 |

書き込みはすべて既存の作法(一時ファイル → rename + 同一ファイルへの直列化)。

**本文は翻訳しない。** 壁打ちの記録は「実行時の記録」なので、後から別言語で開いても
その時どう教えたかは変わらない(CLAUDE.md)。ラベルだけが表示言語に追従する。

**学習者 ID をどう持つか — 認証基盤が無い**
確認結果: `server/index.ts` に認証もセッション管理も無い。localStorage のキーは
`mnd-theme` / `mnd-lang` / `mnd-tab` の 3 つだけ。「ジュニアごと」を成立させるには新しい概念が要る。

| 案 | 長所 | 短所 |
|---|---|---|
| ① localStorage の匿名 ID | 導入コスト 0 | 端末を変えると別人になる |
| ② 画面上のハンドル選択(サーバの `learners.json` に登録、パスワードなし) | 端末を跨げる。チーム内の信頼前提で十分 | 他人になりすませる |
| ③ 認証基盤を入れる | 厳密 | このアプリには過剰 |

→ **推奨は ②。前回選んだハンドルを ① の仕組みで localStorage に覚える。**
  本名でなくハンドルでよい旨を画面に明記する。**ただし §6-1 でユーザー確認が要る。**

**保持量**: 調査履歴は 215 件で 748KB(1 件約 3.5KB)。壁打ちは往復が多いのでこれより増える。
無限追記にはせず、上限を超えたら古い順に落とす(webhook-feed の archive パターンが参考になる)。
具体値は実装時に決める(§6-5)。

## 3. Task 3: クイズモードの設計

### 3-1. 自動生成の設計方針

**(a) 素材の選定はコードで、問題文の生成だけ LLM に任せる。**
「面白い問題を作れ」と丸投げすると、素材から離れた作り話が混ざる。
素材 1 件を確定してから、その 1 件だけを渡して出題文を書かせる。

**(b) プールと適格条件**(§1-1 / §1-2 の実測に基づく)

```
プール = 承認済みナレッジ 8 件
       + 教材適格な調査履歴 152 件
         (!isError && answer >= 400 文字 && calls.length > 0 && source != "scheduled")
```

**(c) 出題形式は素材の性質で決まる(モデルには選ばせない)**

| # | 形式 | 素材 | 隠すもの |
|---|---|---|---|
| 1 | **症状 → 原因を当てる** | ナレッジ | `rootCause` |
| 2 | **症状 → 次の一手を当てる** | 調査履歴 | `calls[]` の 2 手目以降 |
| 3 | **設定 → どのルールに触れるか** | ベストプラクティス | ルール ID と重大度 |

**形式 2 がこの機能の中核。** `query` と `calls[]` の 1 手目だけを見せて
「次にどのツールを叩く? なぜ?」と問う。実際の熟練者の手順が正解データになっているので、
**採点の根拠が主観にならない**(モデルの意見ではなく、実際にそう調べて解決した記録)。

**(d) 回答形式**
自由記述を既定にする(選択肢はカンニングになる)。ただし **L1 の学習者には 3 択**を出す
(白紙で固まらせない)。3 択の誤答は、同じカテゴリの別ルール / 別ナレッジから機械的に作る
(LLM に誤答を創作させない — もっともらしい嘘の選択肢は誤学習の温床になる)。

**(e) 難易度**
`severity`(must → advisory)、`scope`(general → site/device)、
その学習者のそのタグでの過去実績、の 3 つで 1〜3 を決める。既定は学習者の推定レベル。

**(f) 素材が薄いことへの対処(実測 8 + 152 件)**
承認済みナレッジ 8 件は、1 週間毎日 3 問出すと 3 日で尽きる。
→ 当面は**履歴由来の形式 2 が主力**になる(152 件あり、`calls[]` の切り出し位置を変えれば
  同じ調査から複数問作れる)。あわせて Coach から「未承認候補が 66 件ある」ことを
  ナレッジタブへの導線として出すかは §6-2 で確認する。

### 3-2. 出題 → 回答 → フィードバックの流れ

```
出題(素材 1 件 + 形式)
  ↓
学習者が回答(自由記述 / 3 択)
  ↓
採点: LLM に [VERDICT:correct|partial|wrong] マーカーを出させ、それだけを検出する
  ↓
┌ correct → 正解と告げ、「なぜそうなるか」を一言言わせて終える(1 往復)
├ partial → 足りない側面を 1 つだけ問う。次のターンで必ず開示(最大 2 往復)
└ wrong   → まず「そう考えた理由」を聞く(誤概念の特定)。次のターンで必ず開示(最大 2 往復)
  ↓
開示。元になった自社の事例へのリンクを必ず添える(§5-3)
```

**(a) 正誤をモデルの自然文から読まない。**
`[VERDICT:...]` マーカー方式にする理由は `[SKIP:central]` とまったく同じで、
日英を切り替えた瞬間に無言でパースが外れるのを避けるため(CLAUDE.md 第 3 項)。
マーカーは日英どちらの system prompt でも同じ形で指示し、翻訳・全角化を禁じる一文を入れる。
検出後は本文から必ず除去する。

**(b) クイズは壁打ちより早く答えに寄せる(上限 2 往復)。**
壁打ちは「自分の課題を持ち込んでいる」ので粘る価値があるが、
クイズは既に「解こうとしている」状態なので、テンポが学習量を決める。
壁打ちの 3 ターン規則より 1 つ短くする。

**(c) `partial` を用意する理由。**
正誤 2 値だと「方向は合っているが浅い」回答が `wrong` に落ち、junior の意欲を削ぐ。
実際の切り分けは部分点の世界なので、3 値にする。

### 3-3. 同じ事例からの繰り返し出題を避ける

**(a) ナレッジの `refCount` 機構は「考え方だけ」流用し、カウンタは共有しない。**
理由は §1-1(d)。`refCount` は 47 番で「調査プロンプトへ注入された回数」と定義済みで、
Coach が回すと指標の意味が壊れる。

**(b) 別ファイルに同型の記録を持つ**

```
data/coach/material-usage.json
{
  version: 1,
  materials: [
    { kind: "knowledge" | "history" | "rule",
      id: "<entry id / runId / RULE-ID>",
      quizCount: number,
      lastQuizAt: string | null,
      byLearner: { "<learnerId>": { count, lastAt, lastVerdict } } }
  ]
}
```

`store.recordReferences()` と同じ流儀にする:
**使った時点で +1 / 保存に失敗しても throw しない**(記録の失敗で出題そのものを壊さない)。

**(c) 選択は「全体」ではなく「学習者ごと」に見る。**
別の junior にとっては同じ問題が有効なので、共通の `lastQuizAt` で寝かせるのは損。
優先順は **未出題(その学習者にとって) → `lastAt` が古い順**。

**(d) 間違えた素材は意図的に戻す(間隔反復)。**
`wrong` だった素材は 3 日後・10 日後に**別の形式で**再出題する。
「繰り返さない工夫」と矛盾しない — **正解した素材は寝かせ、間違えた素材は戻す**、が正しい設計。
形式を変えるのは、問題文ごと暗記されるのを避けるため。

`.go-root` が `--central` / `--mist` / `--up` をローカルに置いているのと同じ流儀で、
`.co-root` にまとめる(グローバルトークンは触らない):

```css
.co-root {
  --coach: var(--accent-amber);              /* 主色。テーマ切替に自動追従 */
  --coach-soft: rgba(242, 166, 90, 0.14);    /* コーチ側バブルの地 */
  --bubble-learner: var(--panel-2);          /* 学習者側は既存トーンのまま */
  --co-radius: 14px;                         /* 既存 3px の角ばりを Coach だけ丸くする */
  --co-avatar: 28px;
}
```

ライトテーマでは amber が薄いと本文が読めないので、`--coach-soft` はライト用に別値を持つ
(`:root[data-theme="light"]` 側で上書き。既存のテーマ切替の仕組みに乗る)。

**(c) 具体化するもの**

| 要素 | 方針 |
|---|---|
| バブル | 角丸 14px。コーチ側は左上の角だけ落とす吹き出し形、学習者側は右上。**左右配置で話者を分ける** |
| アバター | **絵文字 1 つ**(🐤 等)。画像アセットは持ち込まない — 既存も `🌐` / `☀` / `☾` を絵文字で出しており、オフライン動作・リポジトリ肥大・CSP のどれとも衝突しない |
| フォント | 本文は既存の `--sans`(IBM Plex Sans JP)のまま。**`--mono` は Coach では使わない**(等幅はログ画面の顔になる) |
| 情報密度 | 既存タブより低くする。1 画面に詰め込まない。行間を広げる |
| ヒント段階 | 「💡 ヒント 1/3」の形で**残り回数を見せる**。出し渋られている不安を消すのと、粘る価値があることを同時に伝える |
| 文言 | **辞書の値だけで調整**する。「実行」→「やってみよう」、「エラー」→「うまくいかなかったみたい」 |
| **用語は崩さない** | SSID を「電波の名前」と言い換えない。**用語は正しいまま、地の文だけをやわらかくする**。崩すと現場で通じない人が育つ |
| アクセシビリティ | 話者を色だけで区別しない(アバター + 左右配置 + `aria-label`)。ダーク / ライト両対応は既存と同じく必須 |

**(d) i18n**
Coach は文言量が多い(既存 1,440 キーに対して **+150〜200 キー**と見積もる)。
`ja.json` / `en.json` の同時追加は必須。カジュアルなトーンは**両言語で作る**
(英語だけ硬い、という状態を作らない)。

## 5. Task 5: 追加機能の設計方針

### 5-1. エスカレーション導線

**(a) ボタンは 2 つに分ける**

| ボタン | 動作 |
|---|---|
| 💡 ヒントをもう 1 つ | `hintLevel += 1` |
| 🔓 もう答えを教えて | `hintLevel = 3`(即開示) |

**(b) 「答え」には 2 種類あるので、行き先を分ける**

1. **教材の中の答え** → Coach がそのまま開示する。MCP を呼ばないので速い。
2. **今のネットワークの状態が知りたい** → **それは Coach の仕事ではない。**
   「調査タブで今の状態を調べる」ボタンを出し、既存の `onInvestigate({ query, site })` に積んで
   タブを切り替える。**自動実行はしない**(15 番の作法どおり、文面を用意するだけ)。

**(c) 渡すクエリ文の組み立て**
サーバ側で文章を作らない。**学習者の発話をそのまま入れる** + サイトが特定できていれば `site` を載せる、
に留める。定型部分が要る場合はプレースホルダ付きテンプレートを日英辞書に置いて `t()` で埋める
(CLAUDE.md「動的に組み立てる文字列」)。

**(d) 障害対応中モード**(§2-3(d))が本命
エスカレーションを**押させる**設計は、「押していいのか」の判断を junior に負わせている。
セッション開始時の「今、障害対応中?」で最初から開示モードに入れる方が安全。
実際に困っている人は、ヒントを断る余裕もないことが多い。

**(e) 記録**
エスカレーションは**弱点シグナルとして必ず記録する**(どの話題で、何ターン目に押されたか)。
「答えを見た」こと自体は責めない。何度も同じ話題で押されるなら、それは教材か教え方の問題。

---

### 5-2. 弱点の記録

**(a) 記録するのは、コードで観測できる事実だけ。** モデルの自然文評価は保存しない。

| 場面 | 記録する値 |
|---|---|
| 壁打ちセッション | `{ topicKeys[], turns, maxHintLevel, escalated, incidentMode, startedAt, endedAt }` |
| クイズ 1 問 | `{ materialId, kind, verdict("correct"/"partial"/"wrong" ← マーカー由来), hintsUsed, answeredAt }` |

**(b) 話題キー(`topicKey`)はナレッジのタグ語彙をそのまま使う。**
承認済みナレッジは 1 件あたり 4〜8 個のタグを持ち(実測)、語彙が既に揃っている。
ベストプラクティスのルール ID / カテゴリも同じ軸に載せる。
**新しい分類体系を作らない** — 既存の語彙に寄せる方が、他タブとの相互リンクが素直になる。

**(c) 弱点スコア**

```
weakness(topicKey) = (wrong + partial * 0.5) / attempts  と  平均 maxHintLevel  の合成
```

**`attempts >= 3` になるまで「弱点」として扱わない。** 1 回間違えただけで弱点認定すると、
その話題ばかり出されて嫌になる(この機能で最も起こりやすい失敗)。

**(d) 反映先**

| 反映先 | 方針 |
|---|---|
| クイズの素材選択 | 弱点タグの素材を優先する。**ただし常にではなく 1/3 程度**。弱点ばかり出すと続かない |
| ヒントの初期段階 | 弱点タグの話題では `hintLevel` を 0 ではなく **1 から始める**(苦手なところで空振りさせない) |
| 3 ターン規則 | 弱点タグでは **2 ターン**に短縮する |
| 画面表示 | **学習者本人にだけ**「最近つまずいたところ」を出す |

**(e) 可視範囲は本人のみを既定にする。**
弱点データは人事評価に転用できてしまう。**他人の弱点は見えない**設計にしておくのが、
「Coach に本音で分からないと言える」ための前提になる。
分からないと言えなくなった時点で、この機能は死ぬ。**§6-1 でユーザー確認する。**

**(f) 置き場**: `data/coach/learners.json`。1 ファイル + atomic write は既存プラグインと同じ。

---

### 5-3. 根拠へのリンク提示

**(a) 取得は 2 経路の併用**

1. **モデルの宣言**: `[SRC:knowledge:<id>]` / `[SRC:history:<runId>]` / `[SRC:rule:<RULE-ID>]` を出させ、
   サーバが検出 → 本文から除去 → 構造化して返す
   (`insight-agent.ts` の `detectPlatformJudgments()` / `stripPlatformJudgments()` と同型)。
   **渡した素材の ID 集合に含まれるものだけを採用**し、それ以外は捨てる(存在しない ID の捏造対策)。
2. **サーバが渡した素材一覧**: Coach の回答は必ず素材由来なので、
   **渡した素材 = 根拠の上限**。モデルが挙げなかったものも含めて併記する。

1 だけだと取りこぼし、2 だけだと「実際に使ったのはどれか」が分からない。両方出す。

**(b) 表示**
「📎 元にした記録(N 件)」の折りたたみ。中身は 53 番の `ReferenceCard`
(見出し + 一言 + リンク、`RuleReference.tsx:98-141`)と同じ構成にする。
ルールの `references[]` の外部 URL は `target="_blank" rel="noreferrer"`
(既存の `view/safeHref.ts` の作法に倣う)。

**(c) ネタバレの制御 — ソクラテス式との唯一の正面衝突**

根拠リンクを開くと `rootCause` / `action` が読めてしまう。これは設計上の矛盾なので明示的に扱う:

| hintLevel | リンクの見せ方 |
|---:|---|
| 0〜2 | **「元になった記録があるよ(2 件)」とだけ見せる。** タイトルも本文も畳んだまま |
| 3(開示後) | 全部展開可能。**元記録を読ませることが次の学習**になる |

「根拠が無いと信用できない」と「答えが見えると学習にならない」は本当に両立しないので、
**時間軸で分ける**(先に考えさせ、後で確かめさせる)。
