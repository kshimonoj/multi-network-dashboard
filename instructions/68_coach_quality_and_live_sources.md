# 68: Coachの回答品質改善 — 原因調査 + ライブ情報ソース(MCP)の追加

## 背景・問題

- rogue APアラートについて壁打ちで質問したところ、Coachが「電波の話か有線の話か」という技術的に誤った前提を提示した(rogue APは本質的に無線側の事象であり、有線側の話にはなり得ない)
- 同じ質問をNetwork Investigation(Insight Agent)に投げると、RSSI実測値・実際のアラーム件数・正規SSIDとの照合まで踏まえた正確な回答が返る。Coachの回答品質はInsight Agentより明らかに劣る
- 原因の仮説(要検証):
  1. Coachの回答根拠は現状、Knowledge/調査履歴/ベストプラクティスという**静的な蓄積データからの検索のみ**で、Insight Agentのような**ライブなCentral/Mist問い合わせ(MCP経由)を行っていない**。今まさに起きている個別事象について聞かれた時、根拠が薄い(または無い)状態でも「それらしい質問」を作ろうとして、誤った前提を作文してしまっている可能性がある
  2. 65〜67番で調整した関連度しきい値(調査履歴層0.05まで緩和)が「弱い根拠でも無理に使ってしまう」傾向に拍車をかけている可能性がある
  3. 66・67番で追加したガードレール群(APP_UI_RULES、hintLevel強制構造、発話分類によるsearch text制限)がプロンプトを複雑化・窮屈にしすぎて、モデルの素直な推論力を圧迫している可能性がある

## 今回の対応方針(ユーザー決定)

- **Coachの情報ソースを、Insight Agentと同じ(MCP経由のライブ問い合わせを含む)に広げる**
- 情報ソースは絞らない。ただし優先度を付ける: **過去の調査結果・ナレッジを優先的に使用**し、それだけでは根拠が薄い/古い/対象外の場合に、ライブなCentral/Mist問い合わせ(MCP)で補強・裏取りする
- ソクラテス式の応答スタイル(答えをそのまま返さずヒントで気づきを与える)自体は維持する。ライブデータは「回答の根拠」を強化するために使うのであって、Coachが直接回答を垂れ流す機能に変質させるわけではない

## タスク

### Task 1: 原因調査

1. 実際にrogue APの質問を再現し、Coachに渡っている最終的なsystem prompt全文・取得された教材(材料)の中身を確認する。「元にした記録が5件ある」とされていた根拠が実際どんな内容だったか(rogue APと無関係な低関連度の記録が混ざっていないか)を確認する
2. 65〜67番で調整した関連度しきい値(特に調査履歴層の0.05)が、この事例でどう影響したかを確認する
3. 66・67番のガードレール(APP_UI_RULES等)がプロンプト全体の長さ・複雑さにどう影響しているか、それが回答品質に影響していそうかを確認する(可能であればガードレール追加前後のプロンプト差分やモデル挙動を比較する)
4. 上記を踏まえ、根拠が薄い時にCoachが「わからないので一般論で聞く」方向ではなく「もっともらしい誤りを作る」方向に倒れている実例を、他の話題でも探して確認する

### Task 2: ライブ情報ソース(MCP)の追加

1. Insight Agentが使っているMCPツール(central-mcp/mist-cloud)へのアクセスをCoachにも追加する
2. 優先順位付けロジックを実装する: (a)まず自社のナレッジ・調査履歴を検索する、(b)ヒットが薄い・古い・対象外の場合、または今まさに起きている個別事象についての質問と判断される場合に、ライブなMCP問い合わせで補強する、という段階的な方針にする(64/65番で設計した「自社ナレッジ最優先→調査履歴→ベストプラクティス」の段階的フォールバックの延長として、ライブMCPを追加の層として組み込む)
3. ライブMCP問い合わせの結果は、Insight Agentと同様に事実として扱い、Coachの回答(ヒント)の技術的な正しさを担保する材料として使う。ただし出し方はソクラテス式のまま維持する(ライブで正確な事実を把握した上で、その事実をそのまま開示するのではなく、事実に基づいた正しい前提の質問・ヒントを作る)
4. Central APIのレート制限(秒10回程度・アカウント全体共有)に注意する。壁打ち(チャット)では都度ライブ問い合わせを行う可能性があるが、クイズ出題モードは基本的に過去事例からの出題なのでライブ問い合わせは不要と考えられる(必要かどうか判断する)
5. 62番で判明したMCPタイムアウト(`plugins/network-investigation/mcp.ts:511`のDEFAULT_TIMEOUT_MS=240000)のような制約がCoach側でも問題にならないか確認する

### Task 3: ガードレールの見直し(Task 1の調査結果次第)

1. Task 1でガードレール(66・67番分)がプロンプト複雑化により品質を下げていると判明した場合、プロンプトの簡潔化・整理を検討する(66・67番で実現した安全性・状態管理の効果自体は落とさない範囲で)
2. 関連度しきい値がTask 2のライブMCP追加によって見直しが必要になる場合(静的データが薄い時にライブ確認へ回すトリガーとしてしきい値を使う等)、設計を調整する

### Task 4: 動作確認

1. rogue APの質問を再現し、Insight Agentと遜色ない技術的正確さのヒントが返ることを確認する(添付されていたInsight Agentの回答内容と比較する)
2. 他の複数の話題(無線障害・セキュリティ・スイッチ障害等)でも、ライブMCPによる裏取りが機能し、明らかな技術的誤りが出ないことを確認する
3. ソクラテス式の応答スタイル(hintLevel管理、3ターン規則、エスカレーション、根拠リンク)が引き続き正しく機能することを確認する(66・67番の修正への回帰が無いことを含む)
4. クイズモードに副作用が出ていないことを確認する
5. Central APIレート制限への配慮(呼び出し頻度・タイムアウト処理)が適切であることを確認する
6. 実装完了後、本番Dockerコンテナのrebuildまで行い、本番ポート(8092)での動作確認まで実施する(標準運用ルール通り)
