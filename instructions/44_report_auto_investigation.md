# 44: レポートの重大な問題を自動事前調査する(MCP込みの本格調査を事前実行)

## 背景

現在のレポートの「検出された問題」は、集計データをもとにしたLLMの簡易分析(根本原因・影響範囲等)は含まれているが、MCP経由でCentral/Mistに実際に問い合わせる本格的な調査はしていない。「調査する」ボタンを押すとネットワーク調査タブに遷移してそこから調査が始まるため、結果が出るまで時間がかかる。

Webhookログで実装済みの「重大アラートの自動事前調査」(enrich.ts)と同じ考え方で、**レポート生成時に重要度の高い問題だけ、あらかじめMCP込みの本格調査を済ませておく**。

## 方針(確定事項)

- 対象: 重要度が「重大」かつ、(新規の問題 または 再発が続いている問題)に該当するもののみ
- 上限: 1回のレポート生成につき最大2〜3件程度(Webhookの自動事前調査の上限設定と同様の考え方で、設定可能にする)
- 重複防止: 同一の問題(既存の名寄せキー/dedup keyで判定)は、過去のレポートで既に自動調査済みであれば再実行しない(Webhookの「同一アラートは1回のみ」と同じ考え方だが、時間窓ではなく名寄せキーの既調査履歴で判定する)
- 調査済みの問題は、レポート画面で「調査する」ボタンの代わりに**「調査結果を見る」**(pendingHistoryFocusで既存の実行スレッドに直接ジャンプ、18/19番のパターンを流用)を表示する

## タスク

### Task 1: 自動事前調査のトリガー実装

1. 日次レポート生成処理(41番のgenerate.ts等)の中で、確定した「検出された問題」のうち、上記条件に該当するものを抽出する
2. 該当する問題ごとに、既に自動調査済みか(名寄せキー単位の履歴、Webhookのstate.jsonと同様の記録の仕組みを新設または流用)を確認し、未調査のものだけ対象にする
3. 上限件数(設定可能、既定2〜3件)を超えないようにする

### Task 2: MCP込みの本格調査の実行

1. 対象の問題ごとに、既存のInsight Agent(runInsightAgent、claude CLI経由でMCPを使う本来の調査)をバックグラウンドで実行する。クエリは問題の内容(対象機器・重要度・根本原因の簡易分析・発生履歴)を踏まえて自動生成する(Webhookのbuildレポート/buildAutoQueryと同様のパターン)
2. 実行結果のrunId(セッションID)を、その問題のレコードに紐付けて日次レポートのJSON(またはstate.json相当)に保存する
3. この調査もコストが発生するため、既存の自動事前調査と同様にログに記録し、実行状況が追えるようにする

### Task 3: フロントエンドの表示切り替え

1. レポートの「検出された問題」表で、自動調査済みの問題には「調査結果を見る」ボタンを表示し、pendingHistoryFocus経由でネットワーク調査タブの該当スレッドへジャンプできるようにする(18/19番のタイムアウトフォールバックも流用する)
2. 未調査の問題は従来通り「調査する」ボタン(クエリ事前入力のみ)のままにする
3. 自動調査中(実行途中)の問題があれば、その状態が分かる表示(例: 「調査中」バッジ)を検討する。必須ではないが、実装が容易であれば入れてよい

### Task 4: 動作確認

1. 実際に重大かつ新規/再発継続の問題がある日でレポートを生成し、自動調査が実行されることを確認する
2. 同じ問題が翌日以降のレポートにも出てきた場合、再度自動調査が実行されない(重複防止)ことを確認する
3. 上限件数を超える重大な問題がある場合、上限までしか自動調査されないことを確認する
4. 「調査結果を見る」ボタンから実際に過去の調査スレッドに正しくジャンプできることを確認する
5. 既存のWebhookログ側の自動事前調査・その他の機能に影響が無いことを確認する
6. `docker compose up -d --build`で反映し、実画面を確認する

## 完了報告

verified-report形式で報告すること。特に:

- 自動事前調査のトリガー条件・上限件数・重複防止の実装内容
- 実際に自動調査が発火したケースの内容(対象問題・生成されたクエリ・結果概要)
- 重複防止・上限件数の動作確認結果
- 「調査結果を見る」ボタンの動作確認結果
- 既存機能への影響が無いことの確認
- `docker compose up -d --build`後の反映確認結果

git操作は行わないこと。
