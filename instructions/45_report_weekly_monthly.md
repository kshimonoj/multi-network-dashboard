# 45: 週次/月次レポートの集計ロジック(日次の積み上げ方式)

## 前提・確定事項

- 週次/月次は、生データへの再クエリを行わず、**蓄積済みの日次レポート(41番、`data/reports/daily/*.json`)を集計する方式**にする(コスト削減のため確定済みの方針)
- 43番で作成済みのレポートタブUIは、週次/月次選択時に「準備中」表示になっている。今回はその実データ版に差し替える
- 生成タイミング: 週次は毎週月曜、月次は毎月1日(いずれも既定値。設定で変更可能にする、日次の9:00設定と同様のパターン)
- 週次/月次の自動事前調査(44番の仕組み)は、対象期間内で日次レポート生成時に既に実行済みのものをそのまま参照する形でよい(週次/月次生成時に新たに調査を追加実行する必要はない)

## タスク

### Task 1: 週次/月次データ構造の設計

1. 週次/月次レポートのデータ構造を設計する。含めるべき内容:
   - KPI(総イベント数・重大アラート数・接続端末数の期間集計、新規の問題数)は、対象期間内の日次レポートの値を合算/平均する
   - 健全性/SLEトレンド: 対象期間内の日次値をそのまま並べたグラフ用データ(週次なら日次点、月次なら週単位に間引く等、実装しやすい粒度でよい)
   - 「この期間に起きたこと」: 対象期間内の日次レポートの「起きたこと」から、重要度の高いものを中心に抜粋・統合する(単純に全日次分を連結すると量が多くなりすぎる場合は、LLMに要約させるか、重要度でフィルタする)
   - 「検出された問題」: 対象期間内の日次レポートの問題を、名寄せキーで集約する(同じ問題が複数日にまたがっている場合は1行にまとめ、再発性や発生日の範囲が分かるようにする)
2. 週次/月次の集計処理自体はLLMを使わず機械的な集計で構わない(コスト削減のため)。ただし「起きたこと」の要約に文章化が必要な部分だけ、必要であれば軽量なLLM呼び出しを検討してよい(集計材料は全て確定済みデータなので、複雑な調査は不要なはず)

### Task 2: 生成処理の実装

1. 週次レポート生成処理を実装する(既定: 毎週月曜、対象は直前の月曜〜日曜)
2. 月次レポート生成処理を実装する(既定: 毎月1日、対象は前月1日〜末日)
3. 対象期間内の日次レポートが一部欠けている場合(生成されていない日がある)、欠けている日を除いた分で集計し、その旨をレポートに記録する(エラーにしない)
4. 対象期間内の日次レポートが1件も無い場合は、週次/月次レポート自体を生成せず、その旨をログに残す

### Task 3: スケジュールと保存

1. 週次は毎週月曜、月次は毎月1日に自動生成するスケジュールを実装する(既存のnode-cron機構を踏襲)。生成タイミングは設定で変更可能にする
2. 起動時の後追い生成(41番で日次向けに実装済みのロジックと同様のもの)を週次/月次にも用意する
3. `data/reports/weekly/YYYY-Www.json`・`data/reports/monthly/YYYY-MM.json`のような形で保存する
4. 保持期間設定(41番の日次と同様のパターン)を週次/月次にも用意する

### Task 4: API・フロントエンドの実データ化

1. `GET /api/reports/weekly`・`GET /api/reports/weekly/:week`、`GET /api/reports/monthly`・`GET /api/reports/monthly/:month`のようなエンドポイントを実装する
2. 43番で作成済みのレポートタブの週次/月次表示(現状「準備中」)を、これらのエンドポイントを使った実データ表示に差し替える
3. カレンダーピッカーの週次/月次選択が、実際に生成済みのデータと連動するようにする(43番で実装済みのカレンダーUIの配線を、実データに差し替えるだけで済むはず)

### Task 5: 動作確認

1. 既に蓄積されている日次レポート(7/26〜8/1等)を使って、週次レポートを手動生成し、内容が妥当か確認する(KPIの合算値、問題の名寄せ集約、起きたことの抜粋)
2. 月次レポートも同様に、蓄積分の範囲で手動生成して確認する(1ヶ月分揃っていない場合は「一部の日のみのデータ」であることが分かる表示になっているか確認する)
3. カレンダーピッカーから週次/月次を選び、実データが表示されることを確認する
4. スケジュール登録・保持期間設定が動作することを確認する
5. 既存の日次レポート・自動事前調査・その他の機能に影響が無いことを確認する
6. `docker compose up -d --build`で反映し、実画面を確認する

## 完了報告

verified-report形式で報告すること。特に:

- 週次/月次データ構造の設計内容
- 実際に生成した週次/月次レポートのサンプル内容(KPI集計・問題の名寄せ集約結果)
- 日次レポートが一部欠けている場合の挙動確認結果
- カレンダーピッカーでの実データ表示確認結果
- スケジュール・保持期間設定の動作確認結果
- 既存機能への影響が無いことの確認
- `docker compose up -d --build`後の反映確認結果

git操作は行わないこと。
