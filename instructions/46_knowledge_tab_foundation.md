# 46: ナレッジタブ(調査結果からの知見候補抽出 + 簡潔な承認フロー + 基本画面)

## 目的

ネットワーク調査(手動・自動問わず)の結果から、今後の調査に役立つ知見を抽出し、人の承認を経てナレッジベースとして蓄積する。**このタスクでは「調査への反映(蓄積したナレッジを次の調査プロンプトに注入する)」は対象外**とし、抽出・承認・蓄積・基本画面までを実装する(反映は47番)。

## 方針(確定事項)

- 承認方式は人の承認を必須とする(完全自動での知識ベース反映はしない)
- 承認の手間を最小化する: 候補は「タイトル・症状・根本原因・対処法」を1枚にまとめたカードで表示し、**「承認」ボタン1クリックで完了**できるようにする(編集・入力は必須にしない)
- 内容を直したい場合のみ「編集して承認」を選べるようにする
- 同一調査から複数候補が出た場合は「まとめて承認」できるようにする
- 既存のナレッジエントリと明らかに重複・類似する候補は、新規追加ではなく「これは既存の◯◯と同じ可能性があります」というマージ提案として表示する
- 未承認の候補数をバッジ表示し、見失わないようにする

## タスク

### Task 1: ナレッジ候補の抽出

1. 以下のタイミングで、調査結果から知見候補を抽出する処理を実装する:
   - Webhookログの自動事前調査が完了した時
   - レポートの自動事前調査(44番)が完了した時
   - 手動のネットワーク調査が完了した時(すべてを対象にするとノイズが多い場合は、一定の条件(例: 明確な原因が特定できた調査のみ)に絞ってよい。判断が難しければ、まずは自動事前調査(Webhook・レポート由来)のみを対象にし、手動調査は次段階の拡張候補として完了報告に記録する形でもよい)
2. 抽出は軽量なLLM呼び出し(claude CLI、MCP不要)で行い、以下の項目を生成する:
   - タイトル・症状(どんな状況で当てはまるか)
   - 根本原因
   - 対処法/次のアクション
   - 適用範囲(特定のデバイス/サイト固有か、一般的なパターンかを示すタグ)
   - 出典(元になった調査のrunId、生成日時)
3. 生成した候補は`status: "pending"`として保存する(承認前は正式なナレッジとして扱わない)

### Task 2: 重複検出

1. 新規候補が既存の承認済みナレッジと類似していないか確認する仕組みを実装する(タイトル・タグ・対象デバイス等の一致度で判定する簡易的なものでよい。高度な埋め込み検索等は不要)
2. 類似すると判定された場合、候補に「類似候補あり」のフラグを付け、承認画面でその既存エントリと並べて表示し、「マージする」(既存エントリを更新する)か「別エントリとして承認する」かを選べるようにする

### Task 3: 承認フローの実装

1. バックエンドに、候補の一覧取得・承認・却下・編集して承認・まとめて承認のAPIを実装する
2. 承認されたものは`status: "approved"`として正式なナレッジエントリになり、却下されたものは`status: "rejected"`として保持する(完全削除はしない。誤って却下した場合に見返せるように)

### Task 4: 「ナレッジ」タブの基本画面

1. 新しいタブ「ナレッジ」を追加する
2. 未承認の候補一覧(カード形式、承認/編集して承認/却下/まとめて承認のボタン)を表示する
3. 承認済みのナレッジ一覧(検索・タグでの絞り込みができるとよい)を表示する
4. 各ナレッジエントリから、出典の調査結果(runId)へ「調査結果を見る」で遷移できるようにする(既存のpendingHistoryFocusパターンを流用)
5. 未承認件数のバッジをタブ名の横等に表示する

### Task 5: 動作確認

1. 実際にWebhookログまたはレポートの自動事前調査を1件実行し、ナレッジ候補が生成されることを確認する
2. 候補を「承認」ボタン1クリックで承認できることを確認する
3. 「編集して承認」で内容を修正してから承認できることを確認する
4. 意図的に類似する候補を2つ作り、重複検出とマージ提案が機能することを確認する
5. 却下した候補が完全に消えず、却下済みとして確認できることを確認する
6. 未承認件数バッジが正しく増減することを確認する
7. ダークモード・日英切替の表示を確認する(i18n辞書に新規文言を追加すること)
8. `docker compose up -d --build`で反映し、既存機能に影響が無いことを確認する

## 完了報告

verified-report形式で報告すること。特に:

- 候補抽出の対象範囲(手動調査を含めたか、含めなかった場合の理由)
- 実際に生成された候補の実データサンプル
- 承認・編集して承認・却下・まとめて承認それぞれの動作確認結果
- 重複検出・マージ提案の動作確認結果
- i18n・ダークモードの確認結果
- `docker compose up -d --build`後の反映確認結果

git操作は行わないこと。
