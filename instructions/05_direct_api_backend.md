# 05: Central/Mist直接APIダッシュボードのバックエンド基盤(multi-network-dashboard)

## 前提・背景

現在の調査ページ(network-investigation)はMCP経由(central-mcp-server/mist-cloud)でデータを取得している。今回新設する別タブのダッシュボードは、**MCPを使わずCentral/Mistの直接REST APIを叩く**方針。認証情報は既存central-mcp-http用の`.env`を流用する(05番の前段で決定済み)。

このファイルではバックエンド(認証・APIクライアント・エンドポイント・レート制限対策)のみを扱う。フロントエンドUI(新タブ・Global OverviewのMAP)は06番で別途行う。

## タスク

### Task 1: 認証情報の形式調査(B-15, B-16)

1. `~/claude/central-mcp-http/`の`.env`を確認し、Central APIの認証方式(OAuth2クライアントID/シークレット、リフレッシュトークン、ベースURL等)を特定する
2. `~/.claude.json`のmist-cloud定義を確認し、Mist APIの認証方式(Bearerトークンの形式、有効期限、ベースURL)を特定する。このトークンが直接REST呼び出し(`api.mist.com`等)にそのまま使えるか、MCPサーバー固有のラップがされていないかを確認する
3. どちらも本アプリ(`multi-network-dashboard`)の`.env`に必要な値をコピーする(central-mcp-http側の`.env`自体は変更しない、値の複製のみ)
4. 調査結果を`instructions/05_findings.md`に記録する。認証情報の値そのものは記録せず、形式・入手元・有効期限の有無のみ記載すること

### Task 2: レート制限を考慮したポーリング設計

1. Central APIについては、LPVプロジェクトで採用した方針(bulk一覧エンドポイントへの置き換え、trend系は低頻度バックフィル)を踏襲し、可能な限りbulkエンドポイントを使う設計にする
2. ポーリング間隔は、central-mcp-http側のTTLキャッシュ(読み取り系1日/5-10分)と重複しない範囲で、本ダッシュボード独自に妥当な間隔(例: 1-5分程度)を設定する。秒間10回のレート制限(アカウント全体で共有)を圧迫しないことを最優先する
3. Mist APIについても同様にレート制限への配慮を行う(Mist側のレート制限値も分かれば調査して記録する)

### Task 3: バックエンドAPIクライアント・エンドポイントの実装

1. `multi-network-dashboard`のサーバー側に、Central直接REST・Mist直接RESTそれぞれのAPIクライアントモジュールを新設する(MCPサーバーは経由しない)
2. 既存のサイト→プラットフォーム対応表(site-map.tsで管理しているもの)を流用し、各サイトがCentral/Mistどちらに属するかを判定する
3. NetViewのスクリーンショットで示したような情報(サイト数、デバイス数、接続クライアント数、アクティブアラート数、ベンダー別のAP/Switch/Gateway台数と稼働状況、サイト別内訳)を取得・集計するAPIエンドポイントを実装する。具体的なエンドポイント設計・レスポンス形式は実装側の判断でよい
4. 取得したデータをメモリ内または軽量なキャッシュ(ファイルベースでよい)で一定時間保持し、Task 2で設計したポーリング間隔を守る

### Task 4: 動作確認

1. 実際にCentral/Mist双方から直接APIでデータが取得できることを確認する(実データでの疎通確認)
2. レート制限に抵触していないこと(呼び出し回数・間隔)を確認する
3. `docker compose up -d --build`で反映し、`/health`が正常であることを確認する

## 完了報告

verified-report形式で報告すること。特に:

- Central/Mist認証情報の調査結果(値そのものは含めない)
- 採用したポーリング間隔とその根拠
- 実データでの疎通確認結果
- レート制限への配慮が実際にどう反映されたか

git操作は行わないこと。フロントエンドUIの実装はこの指示書のスコープ外(06番で対応)。
