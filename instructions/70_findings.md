## 1. Task 1: 応答速度・使用モデル

### 1-0. 現状のモデル構成(調査結果)

Coach は**壁打ち・クイズ出題・採点・ライブ問い合わせのすべてで同じ 1 つのモデル**を使う。

```
plugins/coach/agent.ts  defaultModel()
  = process.env.COACH_MODEL || process.env.NETINV_MODEL || "sonnet"
plugins/coach/store.ts  settings.model(data/coach/settings.json / API から変更可、既定 null)

壁打ち  api.ts        : settings.model || defaultModel()
出題    quiz.ts:159   : settings.model || defaultModel()
採点    quiz.ts:234   : settings.model || defaultModel()
ライブ  api.ts → fetchLive({ model: settings.model || defaultModel() })
```

本番の記録 76 ターンはすべて `model: "sonnet"`(`settings.json` は未作成で、`NETINV_MODEL` の
既定 `sonnet` がそのまま効いている)。**用途別に分ける口は無かった。**

### 1-1. 主因 — ライブ層(確定)

`data/coach/sessions.jsonl`(45 セッション / 76 ターン)を集計した。

**注意:** ターンに記録されている `durationMs` は **claude 本体の生成時間だけ**で、
ライブ問い合わせの時間(`live.durationMs`)は別フィールドに入っている。
利用者が待つのは両方の合計なので、合計で測り直した。

| | n | min | p50 | p90 | max | 平均 |
|---|---:|---:|---:|---:|---:|---:|
| 全体(合計) | 76 | 4,289 | **10,255** | 56,317 | 128,296 | 23,141 |
| ライブ使用(合計) | 22 | 18,502 | **46,040** | 88,588 | 128,296 | 54,078 |
| ライブ不使用 | 54 | 4,289 | **6,524** | 23,171 | 53,773 | 10,537 |

ヒント段階別(合計):

| hintLevel | n | p50 | max |
|---|---:|---:|---:|
| 0 | 25 | 5,766 | 46,473 |
| 1 | 26 | 9,179 | 56,592 |
| 3 | 25 | 21,272 | 128,296 |

→ **ライブを引いたかどうかが所要時間をほぼ決めている。** キャッシュヒットを除いた
実際の MCP 問い合わせ 15 回の単体時間は 13.7〜63.3 秒(中央値 37.5 秒)。

**15 回すべてが `central+mist` の両方**を対象にしており、`narrowPlatforms()` が
一度も 1 ベンダーに絞れていなかった(学習者が「どちらの話か」を言わないため)。
そのうえで当時の system prompt が「まず概況ツールから呼ぶ」を要求していたので、
`central_get_summary` と `get_mist_self` の 2 回が毎回固定費になっていた。

### 1-2. Haiku への切り替え — 却下(実測)

同じ教材・同じプロンプトで、モデルだけを変えて回した(いずれも実測)。

**1 巡目**(5 話題 × 1 回):

| 話題 / 段階 | sonnet | haiku |
|---|---:|---:|
| rogue-ap / L1 | 8,307ms | **74,436ms** |
| roaming / L1 | 8,681ms | 27,289ms |
| switch-port / L2 | 6,015ms | 41,531ms |
| dhcp / L3 | 9,573ms | 15,615ms |
| sle-capacity / L1 | 8,396ms | 29,062ms |

**2 巡目**(hintLevel 3 / 2 話題 × 2 回。sonnet と haiku を交互に実行して時間帯の偏りを消した):

| 話題 | sonnet #1 | haiku #1 | sonnet #2 | haiku #2 |
|---|---:|---:|---:|---:|
| rogue-ap / L3 | 12,211ms | 18,824ms | 10,917ms | 36,523ms |
| switch-off / L3 | 13,120ms | 44,910ms | 16,291ms | 64,164ms |

**9 回中 9 回 haiku の方が遅かった。** 加えて品質面で 2 つの実害が出た:

1. **素材があるのに使わない。** `sle-capacity` で教材 3 件が当たっているのに
   「うちの記録には、Capacity SLE についての詳細な説明がないですね」と返し、さらに
   「そもそもどの管理画面でそれを見ているのか」と **66 番で禁止した自アプリ UI 寄りの
   問い返し**に倒れた。
2. **マーカーの規律が落ちる。** `[SRC:history:48cf63b5]` のように UUID を途中で切った。
   `markers.ts` は「渡した素材の id 集合に含まれるものだけ採用」する設計なので、
   これは**根拠リンクが 1 件も表示されない**ことを意味する(捏造対策が正しく働いた結果)。

→ **速度も品質も改善しないので、モデルは sonnet のまま据え置く。**
ライブ層だけ Haiku にする案も検討したが、ライブ層こそマーカー(`[LIVE:premise]` /
`[LIVE:detail]`)の規律が前提と具体値の出し分けを支えているので、同じ理由で採らなかった。

### 1-3. 却下した仮説 2 つ

**(a) ツール往復で時間を食っている → 否。**
claude CLI の JSON 出力に含まれる `num_turns` を実プロンプトで測ったところ、
12 回すべてで **`num_turns = 1`**。Coach は `--disallowedTools Bash Edit Write WebFetch
WebSearch Task` を渡しているが `Read` / `Glob` / `Grep` は許可されたままなので、
「一時ディレクトリを探索して往復が増えているのでは」と疑って `Read`/`Glob`/`Grep` 等も
締め出した版と比較した。

| 話題 | 現行 | 全ツール禁止 |
|---|---|---|
| rogue-ap/L3 | 11,527 / 12,903ms | 15,001 / 15,008ms |
| switch-off/L3 | 12,880 / 14,967ms | 11,076 / 21,038ms |
| roaming/L1 | 7,452 / 6,406ms | 6,063 / 5,970ms |

差はノイズの範囲で、`num_turns` も両方 1。**ツールは元々使われていない。**
時間の内訳は `duration_api_ms` がほぼすべて(例: wall 11,527ms / cli 9,602ms / api 8,885ms)で、
プロセス起動のオーバーヘッドは 1.5〜2 秒。→ **ツール制限は速度対策にならないので変更しない。**

**(b) 自アプリ UI ガード(66 番)の言い直しで 2 倍になっている → 否。**
本番コンテナのログを全期間で数えたところ、`自アプリ UI への言及` の警告は **0 件**
(壁打ち 13 往復中)。言い直しは一度も発火していない。

**副次的な観測(対策なし):** 同じプロンプト・同じモデルでも 7〜45 秒のばらつきがある
(§4 の NEW 5 回: 36.8 / 40.4 / 13.7 / 28.3 / 45.3 秒)。これは API 側の応答時間の揺れで、
アプリ側で制御できる要素が見つからなかった。本番ログの 53 秒・73 秒の外れ値もこれで説明がつく。

### 1-4. 実施した対策 ① ヒント段階 0 ではライブを引かない

ヒント段階 0 は「問い返しだけをする。ヒントは出さない」段階(`prompt.ts` の `HINT_RULES`)で、
**そもそも事実を一切語らない。** ここでライブを引いても、取ってきた前提は
「今どこまで確かめた?」の 1 行に何も足さないまま捨てられていた。

`plugins/coach/live.ts` の `decideLive()` に段階の門を足した(理由コード `earlyStage` を新設)。
**「今どうなってる?」と明示的に聞かれたときは従来どおり引く**(そこを断ると 68 番で直した
回帰に戻る)。あわせて `api.ts` で `decideHintLevel()` をライブ層より**前**に移した
(`decideHintLevel` は素材を見ないので、順序を変えても判定内容は変わらない)。

判定表(実測。`hintLevel` × 発話 × 静的素材の厚み):

| 発話 | hintLevel 0 | hintLevel 1(厚い/薄い) | hintLevel 3(厚い/薄い) |
|---|---|---|---|
| 「今アラートは出てる?」 | ✅ liveIntent | ✅ / ✅ | ✅ / ✅ |
| 「rogue AP のアラートが発生しています」 | ✅ liveIntent | ✅ / ✅ | ✅ / ✅ |
| 「今回のケースだとどう切り分けますか?」 | ❌ earlyStage | ❌ staticEnough / ✅ thinStatic | ❌ / ✅ |
| 「今後こういう事象が起きたら?」 | ❌ earlyStage | ❌ / ✅ | ❌ / ✅ |
| 「rogue AP が発生した場合の手順は?」 | ❌ earlyStage | ❌ / ✅ | ❌ / ✅ |
| 「この状況ではどこから見ますか?」 | ❌ earlyStage | ❌ / ✅ | ❌ / ✅ |

**本番記録に新しいゲートを当て直した結果**(`sessions.jsonl` の全ターンを再生):

```
実際に MCP を叩いたターン: 15 回
  → earlyStage(ヒント段階 0)で消える: 3 回
  → 正規表現の絞り込みで消える:      0 回
  → 残る:                            12 回
削減できた待ち時間の合計: 118 秒 / 残る 440 秒
```

消えた 3 回はいずれも 37.5 / 41.2 / 39.3 秒で、**3 回とも「セッションの 1 ターン目」**だった。
つまり **壁打ちを始めた最初の 1 往復が常に 40 秒前後待たされていた**ことになる。
第一印象がそのまま「遅いコーチ」になっていた部分がここで消える。

### 1-4b. 実施した対策 ② ライブ判定の正規表現を絞った

65〜68 番の版は `今` / `状況` / `発生して` を素通しで拾っており、
「今回は」「今後」「この状況では」「〜が発生した場合」のような**仮定・一般論の質問**でも
ライブが発火しうる状態だった。ライブ 1 回は 13〜63 秒なので、空振り 1 回がそのまま体感になる。

- `今` → `今(?!回|後|度|のところ|まで)`
- `発生して` → `発生して(る|いる|ます)`(「発生して**も**」のような仮定を外す)。`起きて` / `鳴って` / `上がって` も同様
- `状況` 単独を落とした(「今の状況」は先頭の `今` で拾える)

**本番記録での削減効果は 0 回。** 記録されている liveIntent のターンに、絞り込みで
落ちるものは 1 件も無かった。**予防的な変更であり、実測での改善は無い。**

### 1-5. 実施した対策 ③ ライブの system prompt(効果は測定できず)

「必要最小限のツールだけを呼ぶ / 片方のベンダーに寄るならもう一方を叩かない /
上限 8 → 4 回 / 4 回で足りなくてもそこで打ち切る」に書き換えた。

実測(2 問 × 2 巡。キャッシュは毎回クリア):

| 質問 | 旧 tools / ms | 新 tools / ms |
|---|---|---|
| 「今どこかのサイトでアラートが出てますか」#1 | 4 / 28,678 | 4 / 32,766 |
| 「今どこかのサイトでアラートが出てますか」#2 | 4 / 53,929 | 3 / 50,339 |
| 「今この瞬間、オフラインになっているスイッチはありますか」#1 | 4 / 33,394 | **1 / 18,698** |
| 「今この瞬間、オフラインになっているスイッチはありますか」#2 | 2 / 13,998 | 3 / 32,397 |

平均: 旧 3.5 ツール / 32.5 秒、新 2.75 ツール / 33.6 秒。

→ **ツール数の平均はわずかに下がったが、壁時計では有意差が出なかった。**
同じ質問でも 14 秒〜54 秒とばらつく(§1-3 の観測と同じ)ので、n=4 では差が埋もれている。
**「速くなった」とは言えない。** 上限を 4 回に切ったこと自体は、
実測の最大 6 回・中央値 4 回に対する歯止めとして残す。

## 3. Task 3: エスカレーション後にまた質問が返ってくる

### 3-1. 原因(確定)

`plugins/coach/prompt.ts` の `buildChatSystemPrompt()` に、**ヒント段階が 3 なら無条件で**
効く指示が入っていた:

```
if (o.hintLevel >= 3) {
  "【開示したターンで学習を閉じない】",
  "答えを言ったあと、最後に必ず 1 問だけ残す:「次に同じ症状を見たら、最初にどこを見る?」",
}
```

これは retrieval practice(聞いた直後に自分の言葉で言い直させる)を狙ったもので、
**3 ターン規則や段階を踏んで到達した開示では正しい。** 問題は、
**「🔓 もう答えを教えて」で飛んできた開示にも同じ指示が効いていた**こと。
自分から「答えを教えて」と言った相手に、答えの直後もう一度質問を返す形になっていた。

本番データにも実例が残っており、履歴画面で確認できる
(intent=escalate / hintLevel 3 のターンが「次に同じ症状を見たら、最初にどこを見る?」で終わっている)。

### 3-2. 修正

`escalated` と `intent` を `ChatPromptOpts` に足し、
**`hintLevel >= 3 && (escalated || incidentMode)`** のときだけ
retrieval practice の指示を外して `CLOSE_OUT_RULES` に差し替えた。

- 障害対応中モードも同じ立場(即答を求めている)なので同様に扱う
- `forcedDisclosure`(3 ターン規則)と通常の段階進行はこれまでどおり 1 問残す
- **例文は書かない**(68 番の教訓。プロンプトに書いた具体例は出力の雛形として流用される)。
  代わりに「回答の**最後の文を疑問符(? / ?)で終わらせない**」という機械的に守れる形にした
- クイズの解説にも同じ形が入っていたので、`buildQuizGradeSystemPrompt` に `escalated` を
  足した。**「🔓 もう答えを教えて」で来た解説だけ**問いを返さずに閉じ、
  上限往復に達しての解説はこれまでどおり 1 問残す

### 3-3. 実測(修正前 / 修正後 各 3 回)

同じ会話文脈(ローミング不調 / 2 往復済み)から `escalate` を押した場合の、
**回答の最後の文が疑問形かどうか**:

| | 末尾が疑問形 |
|---|---|
| 修正前(65〜69 番の組み立てを再現) | **3 / 3** |
| 修正後 | **0 / 3** |

修正後の 3 回はいずれも、原因(該当する SLE 分類器)と対処(電波設計の見直し)を言い切ってから、
「まず〜を見ると切り分けられるのは覚えておくと便利」のような**任意の提案**で終わっていた。

## 4. Task 4: 「ヒントをもう 1 つ」の不自然な前置き

### 4-1. 原因(確定)

`buildChatUserPrompt()` は、発話が無いターンでも**偽の発話**をプロンプトに置いていた:

```
<今回の相手の発言>
(発言なし。ヒントの続きを求めています)
</今回の相手の発言>
```

モデルはこれを**学習者が言ったこと**として読み、その内容に言及していた。

本番データ(`sessions.jsonl`)に実際の回答が 1 件残っており、その 1 行目がこれ:

> 今回の相手の発言は「ヒントの続きを求めています」だけで、SLE の中身がまだ報告されてない状態だね。

**`ヒントの続きを求めています` という文字列は、コードベース中この偽の発話にしか存在しない**
(`grep` で確認済み。修正後に残っているのは説明コメントだけ)。
モデルがこの文字列をそのまま引用しているので、**発生源は一意に特定できた。**

なお指摘のあった例は intent=hintMore / hintLevel=3 のターンで、
ヒント内容(Coverage / Capacity / Roaming のどれが赤いか)自体は良い内容なので、
**前置きだけを取り除き、内容と末尾の問いはそのまま残す**方針にした
(hintMore による段階進行は Task 3 の「答えを求められた開示」には当たらないため)。

### 4-2. 修正

1. **ボタンを発話欄に入れるのをやめた。** `buildChatUserPrompt` に `intent` を渡し、
   発話が空のボタンターンでは `<今回の相手の発言>` を出さず、代わりに
   `<今回の操作>相手は「ヒントをもう 1 つ」ボタンを押しました。続きのヒントを求めています。</今回の操作>`
   を出す。発話とボタンが両方ある経路(現状 View には無い)でも壊れないよう、両方出せる形にした。
2. **system prompt に `BUTTON_TURN_RULES` を追加**(`intent !== "ask"` のとき)。
   「これは情報の追加ではなく続きの要求」「『発言が無い』『情報がまだ報告されていない』の
   ような前置きを書かない」「直前の問いを繰り返さず必ず一段進める」。

### 4-3. 実測 — **症状そのものの再現には失敗した**

前置きを検出する正規表現を当てて、修正前の組み立てで **10 回**(2 シナリオ × 5 回)流したが、
**前置きは 0/10 で再現しなかった。** 低頻度の挙動(本番 76 ターン中 1 件)で、
修正前後の発生率を数字で比べることはできていない。

修正後も同条件で 10 回流し、**前置きは 0/10**(こちらも前置き無し)。

→ **「原因の特定は確実(§4-1 の文字列一致)だが、修正の効果を発生率で示せてはいない」**
のが正確な状態。構造上の発生源は取り除いてあるので再発しないはずだが、
それは推論であって実測ではない。
