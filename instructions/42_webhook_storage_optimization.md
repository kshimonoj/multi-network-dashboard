# 42: Webhookログの保存方式最適化(日次レポートのデータ欠落防止)

## 背景

41番で判明した通り、現在のWebhookログの保存は上限件数(`WEBHOOK_FEED_MAX_ITEMS`、実測3000件)を超えると古いものから溢れる方式になっている。Mistだけで1日2949件というデータ量が実際に記録されており、複数日分が溜まると簡単に上限を超えてしまう。この状態では、日次レポートが「その日、実際には何件あったか」を正確に集計できない(溢れて消えた分は集計不能)。

## 方針

**UIでの一覧表示(直近を見るためのもの)と、レポート生成が読みに行くデータ(日ごとの正確な件数が必要)の要件は別物**と捉え、保存方式を見直す。

## タスク

### Task 1: 現状の保存方式の確認

1. `WEBHOOK_FEED_MAX_ITEMS`が実際にどう使われているか(単一のローリングバッファなのか、日付ごとに分かれているか)をコードで確認する
2. 現在の実装が「合計件数で上限に達すると古いものから削除」という挙動である場合、それが日次レポートの集計にどう影響しているか(41番で確認済みの内容と合わせて）を`instructions/42_findings.md`に記録する

### Task 2: 保存方式の見直し

1. Webhookログの生データを、**日付ごとのファイル(例: `data/webhook-feed/daily/YYYY-MM-DD.jsonl`)に分けて保存**する方式に変更する。これにより、ある日の件数がどれだけ多くても、その日のファイル自体が上限に影響されて欠落することがなくなる
2. UI(Webhookログタブの一覧表示)は、パフォーマンスのため直近の日数分・または直近N件のみを読み込んで表示する形にする(表示上の上限は残してよいが、これは「見せる量」の制限であり「保存する量」の制限ではないことを明確に分離する)
3. 日次レポート生成(41番で実装済み)は、この日付ごとのファイルから対象日のデータを直接読み込むように変更し、上限に左右されず正確な件数を集計できるようにする
4. 全体の保存量が際限なく増え続けないよう、保存自体にも保持期間設定(既定は例えば90日、設定で変更可能)を用意する。これはWebhookログタブの既存のRetention設定と統合するか、別枠にするか実装しやすい方でよい

### Task 3: 移行

1. 既存の保存データ(現在の単一ファイル/上限付きの形式)を、新しい日付ごとの形式に移行する処理を用意する(既存データが失われないようにする。既に上限を超えて欠落してしまっている過去分は復元できないため、その旨を完了報告に明記すればよい)

### Task 4: 動作確認

1. 意図的に大量のダミーWebhookイベント(1日で3000件を超える量)を投入し、日付ごとのファイル方式でも欠落せず保存されることを確認する
2. その状態で日次レポート生成(41番のAPI)を実行し、正確な件数が集計されることを確認する(以前のように上限で切られていないことを確認する)
3. Webhookログタブの一覧表示が、引き続き妥当な速度で表示されることを確認する(全件を毎回読み込んで重くなっていないか確認する)
4. 既存の「調査する」「調査結果を見る」等の機能に影響が無いことを確認する
5. `docker compose up -d --build`で反映し、実画面を確認する

## 完了報告

verified-report形式で報告すること。特に:

- 現状の保存方式の確認結果
- 新しい保存方式の設計(ファイル構成、UI表示との分離方法)
- 移行結果(既存データの扱い、欠落済み過去分がある場合はその明記)
- 大量データでの動作確認結果(欠落しないこと、レポート集計が正確になること、UI表示速度への影響)
- `docker compose up -d --build`後の反映確認結果

git操作は行わないこと。
