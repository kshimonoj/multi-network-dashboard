# 67_findings — Coach の 2 つの既知課題(エスカレーション時の根拠欠落 / 短い相槌での話題リセット)

66_findings.md §5-(a)(b) で「66 番では直していない既存の挙動」として残した 2 件を修正した。

---

## 1. 原因は 1 つだった

症状は 2 つに見えていたが、**原因は同じ 1 点**だった。

> `api.ts` の `/chat` が、**そのターンの発話の中身を見ずに**、
> 毎ターン「検索文」と「話題キー」をゼロから作り直していた。

継続のターン(相槌・ボタンだけ)にも新規の問いと同じ処理を当てるため、
片方は「検索文が空になる」、もう片方は「話題キーが素材から捏造される」形で表面化していた。

### 1-1. Task 1: エスカレーションで教材が 0 件になる

```ts
const searchText = question || session.turns.at(-1)?.question || "";
```

- 「🔓 もう答えを教えて」はボタンなので `question` が空 → 直前ターンの質問文にフォールバックする
- ところが **直前ターンが「💡 ヒントをもう 1 つ」だと、その `question` も空**
  → `searchText` が空文字列 → `collectMaterials()` は空クエリで即 `[]` を返す
- 結果 `hintLevel=3` なのに教材 0 件。プロンプトは `noMaterials` 分岐に入り、
  「うちの記録には無い」と返る = **開示の保証が空振りし、根拠リンクも出ない**
  (`Evidence.tsx` は `materials.length === 0` で `return null`)

実データ(`data/coach/sessions.jsonl`、修正前)で確認:

| ターン | intent | question | materials | citedIds |
| --- | --- | --- | --- | --- |
| 7 | escalate | (空) | **0** | 0 |
| 8 | escalate | (空) | **0** | 0 |
| 12 | escalate | (空) | **0** | 0 |
| 11 | hintMore | (空) | 5 | 0 |

11 だけ 5 件あるのは、直前ターンに発話(`"test"`)があったため。
**エスカレーション経路が特別扱いされていたのではなく、「発話が空のターンが連続すると落ちる」**構造だった。

66_findings §5-(a) が書いていた「『もう答えを教えてください』だけを送る」ケース(= 文で送る場合、
intent は `ask`)も同じ穴で、その短文で教材を引きに行って外していた。

### 1-2. Task 2: 短い相槌で往復数がリセットされる

```ts
export function extractTopicKeys(text, matched) {
  const out = topicKeysOf(text);
  if (out.size === 0 && matched) {           // ← ここ
    for (const m of matched.slice(0, 2)) for (const t of m.meta.tags.slice(0, 2)) out.add(t);
  }
  ...
}
```

- 相槌は話題キーが取れない → **当たった素材のタグを話題キーとして借りる**
- 素材検索は空クエリでない限り必ず何かを返すので、借りたキーは**毎ターン別物**になる
- `decideHintLevel()` の `newTopic = firstTurn || (topicKeys.length > 0 && !sameTopic(...))`
  が真になり、`turnsOnTopic` が 1 に戻る = **3 ターン規則が永遠に発火しない**

実データ(修正前)。1 ターン目の `switch-offline` が 2 ターン目以降に引き継がれていない:

| 発話 | 抽出された話題キー |
| --- | --- |
| 「スイッチが落ちたって連絡が来たとき、最初に何を確かめますか」 | `switch-offline` |
| 「まだ何も確認していなかった。」 | **`rf`, `RF-14`** |
| 「わからない」 | **`pmf`, `methodology`, `marvis`, `resolved`** |

申し送りの仮説(短文が新規トピックの質問と誤認識されている)は**当たっていた**が、
誤認識しているのは発話の意味ではなく、**素材のタグを話題キーに昇格させていたこと**だった。

## 2. 修正

### 2-1. `plugins/coach/utterance.ts`(新規)

学習者の発話を 3 つに分類する。**モデル出力ではなく学習者の入力を見る処理**なので、
CLAUDE.md 第 3 項(モデル出力の自然文パース禁止)には触れない。
立場は `materials.ts` の `JA_SYNONYMS` / `topicKeysOf()` と同じ。

| 種別 | 条件 |
| --- | --- |
| `empty` | 発話なし(💡 / 🔓 のボタンだけ) |
| `continuation` | 相槌の語彙に全体一致 / **または** 短い かつ 発話由来の話題キーが 0 個 |
| `substantive` | それ以外(発話由来の話題キーが立てば、短くても substantive) |

- 相槌の語彙は日英を持ち、**全体一致**で見る(部分一致だと「はい」が「配線」等を巻き込む)
- 「短い」は和文 24 文字 / 英文 6 語。**語数の規則は和文に使えない**
  (空白で切れないので常に 1 語 = どんなに長い日本語の質問も「短い」になる。実装中に踏んだ。
  `CJK_RE` で切り替えている)
- **話題キーが立つ発話は長さより優先して substantive** にする。
  「rogue AP のアラートが出たときは?」のような**短い新しい問い**を潰さないため
  (指示の Task 2-4「過剰修正がないか」への対応)

同じファイルに `buildRetrievalQuery()` / `lastSubstantiveQuestion()` を置いた。

### 2-2. 検索文(Task 1)

継続のターンは**発話自体に検索価値が無い**ので、直近の実質的な質問と今の論点の話題キーを足して引く。

```
substantive          → 発話そのまま(従来どおり)
continuation / empty → 発話 + 直近の実質的な質問 + session.topicKeys
```

- `lastSubstantiveQuestion()` は**相槌のターンを飛ばして**後ろから探す
  (「わからない」を検索文にしても意味が無いため)。1 つも無ければ空でない最後の発話に落とす
- 話題キーを文字列としてそのまま混ぜているのは、`materials.ts` の入口(`topicKeysOf` → `contains`)が
  **タグ表記そのもの**を拾えるため。受け渡し口を増やさずに履歴層の門(話題キー一致)も通せる

### 2-3. 話題キーの二分割(Task 2)

**判定用と記録用を分けた**のが今回の中心。

| 用途 | 使うキー |
| --- | --- |
| 論点が変わったかの判定(`decideHintLevel`) | **発話由来(`topicKeysOf(question)`)だけ** |
| 弱点プロファイルの軸・画面表示・`turn.topicKeys` | 発話由来 → 今の論点 → 素材由来 の順に埋める |

素材由来の穴埋め(`materialTopicKeys()` として `materials.ts` から切り出し)は
**「実質的な発話 かつ まだ論点が決まっていない」ときだけ**許す。
これで相槌が論点を書き換えられなくなり、かつ「話題キーが取れない最初の質問」でも
弱点の軸が空にならない従来の利点は残る。

`extractTopicKeys()` 自体は残してある(`GET /materials` の動作確認用エンドポイントが使っている)。

## 4. 判断したこと

- **相槌の語彙表だけに頼らない。** 語彙表は取りこぼし対策で、主たる規則は
  「短い かつ 発話由来の話題キーが 0 個」。語彙を足し続ける運用にしないため
  (`JA_SYNONYMS` が手書きで増え続けている 65 §9-1 の二の舞を避ける)
- **論点の切り替えは「学習者が自分の言葉で話題を名指ししたとき」だけに限定した。**
  素材のタグから逆算した論点変更は、相手が何も言っていないのに話が変わったことにする判定なので採らない
- **エスカレーション経路を分岐させていない。** 66 番のガード・マーカー・3 層取得の順序は共通のまま、
  入力(検索文)だけを直した。ルートを分けると「エスカレーションのときだけ挙動が違う」箇所が増える
