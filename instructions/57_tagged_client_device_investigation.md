# 57: タグ付きClient/Device専用ビュー — データ調査・タグ設計(実装はまだ行わない)

## 背景・目的

- 特定のClient(端末)やDevice(AP/Switch/Gateway)にタグを付け、そのタグが付いた対象だけに絞った専用ビューを新設したい
- ClientとDeviceは見る観点が異なるため、それぞれに適した情報を出し分ける。特にClientは利用アプリケーションのトラフィック(何を使っているか)を必ず見せる
- タグはこのダッシュボード固有の独自機能とする(ローカルDBで管理、Central/Mistの設定・ラベル機能には一切手を加えない)
- 対応プラットフォームはCentral+Mist両方を最初から。位置付けは新規独立タブ

今回はいきなり実装せず、49番の進め方(調査→設計→次回以降で実装)に倣い、**データ取得可能性の調査とタグ設計の確定まで**を行う。

## タスク

### Task 1: Client向けデータの取得可能性調査

1. Central側(central-mcp)・Mist側(mist-cloud)それぞれで、Clientについて取得可能な情報を洗い出す。特に重点的に確認すること:
   - **利用アプリケーション/トラフィック内訳**(DPI/AppRF/UCC等、プラットフォームによって名称・提供方法が異なる可能性がある。ライセンス要件がある場合はその旨も明記する)
   - 接続品質・SLE系指標(ローミング、認証失敗、RSSI/SNR等)
   - 接続先AP/デバイス、VLAN、IPアドレス等の基本情報
   - 取得できないもの・プラットフォーム間で提供形式が異なるものを明記する
2. 取得手段(central_get_clients等の既存ツール、または新規に必要なツール)を具体的に特定する

### Task 2: Device向けデータの取得可能性調査

1. Central側・Mist側それぞれで、Device(AP/Switch/Gateway)について取得可能な情報を洗い出す
   - 稼働状況・健全性(CPU/メモリ、稼働時間、ファームウェア世代)
   - 無線関連(チャネル利用率、Tx電力、接続クライアント数)/有線関連(ポート状態、PoE使用量)
   - 既存のGlobal Overviewタブやベストプラクティス診断タブ(51番)で既に取得しているデータと重複する部分があれば明記し、再利用できるかを検討する

### Task 3: タグ機構の設計

1. タグの永続化方式を設計する(ローカルDB、既存プロジェクトのdata/配置慣習に合わせる)
2. タグの対象識別子を設計する(Client: MACアドレス、Device: シリアル番号等。Central/Mist両プラットフォームを横断して同一の対象に同じタグを一貫して付けられるようにする)
3. タグの付け方(UI操作のイメージ、複数タグの付与、タグの削除・編集)の設計方針を記載する
4. タグとClient/Deviceの実データを突き合わせる際の性能面の懸念(全Client/Device一覧を都度取得して突合するのか、タグ付き対象だけを個別に問い合わせるのか)を検討する

### Task 4: 画面構成の設計方針(実装はしない)

1. Client向けビューとDevice向けビューをどう分けるか(タブ内サブビュー、切替UI等)の設計方針を記載する
2. Clientビューでのアプリケーショントラフィック表示のイメージ(一覧・グラフ等、既存のレポートタブ等で使っているコンポーネントを再利用できるか)を検討する
3. 今回はワイヤーフレームレベルの設計方針の記載に留め、実装は次回以降に回す
