# 13: 詳細パネルの表示拡大 + Event/Alert一覧の設計検討 + Webhook取り込みの実現性調査

## タスク

### Task 1: サイト/クライアント詳細の表示を拡大する

現状、サイト詳細・クライアント詳細はサイドパネル(画面右側の固定幅オーバーレイ)で表示されており、Health/SLE・デバイス一覧・クライアント一覧・イベント履歴と情報量が多いため窮屈になっている。

1. サイドパネルの固定幅を広げる案と、一覧画面を置き換える形の全画面表示(いわゆるページ遷移相当)に切り替える案を比較検討する。ルーティングライブラリの新規導入までは不要で、既存のタブ切り替え(main.tsxのローカルstate方式)と同じ手法で「Global Overview一覧」⇄「サイト詳細全画面」を切り替える形で構わない
2. 情報量(デバイス最大9台、クライアント最大十数件、イベント最大50件)を踏まえ、全画面表示に切り替える方針を推奨する。ただし実装のしやすさ・既存コードへの影響を見て判断してよい
3. 全画面表示にする場合、「一覧に戻る」導線(戻るボタン等)を用意し、地図・テーブルどちらから開いた場合も同じ画面に遷移するようにする
4. ダークモード両テーマでの表示を確認する

### Task 2: Event/Alert一覧を独立した項目として持てるか検討・設計

現状、Event/Alertはサイト単位で詳細パネルを開いた時だけオンデマンド取得している。これを「Global Overview全体で1つの独立したEvent/Alert一覧画面」として持てるかを検討する。

1. Central・Mistそれぞれに、**組織(org)単位で全サイト分のEvent/Alertを一度に取得できるAPI**が存在するか調査する(サイト単位のAPIを22サイト分ループするのではなく、1回(または少数回)の呼び出しで全サイト分が取得できるかがポイント)
2. 存在する場合、その呼び出しコスト(HTTPリクエスト数、レスポンスサイズ)を確認し、既存の定期ポーリング(3分毎、現在は5分毎に変更済み)に組み込むかオンデマンド専用にするかを判断する
3. org単位の一括取得ができない場合(サイト単位でループするしかない場合)は、22サイト分のループがレート制限に与える影響を試算し、「独立画面としては現実的でない」と判断できるならその根拠とともに見送り、代わりに現状の「サイト詳細パネル内でのみ表示」を維持することを推奨する
4. 実装するかどうかの判断根拠を`instructions/13_findings.md`に記録する。実装する場合は、独立したEvent/Alert一覧画面(全サイト横断、サイト名・重要度・カテゴリでのフィルタ可能)を追加する

### Task 3: Webhookベースのイベント/アラート取得ページの実現性調査(実装はしない)

新しいタブとして、Central/MistのWebhook通知を受け取ってイベント/アラートログを表示するページを検討したいという要望がある。ただし本アプリはユーザーのMacBook上でDocker動作しており、外部(Central/Mistのクラウド側)からの着信を受け付けられる状態にはない点に注意して調査する。

1. Central・Mistそれぞれが、Webhook通知機能(イベント発生時に指定URLへHTTP POSTする仕組み)を提供しているか確認する
2. 提供している場合、着信を受けるために何が必要になるか整理する(固定グローバルIP、リバースプロキシ/トンネル(ngrok等)、ポート開放、HTTPS証明書等)。現在のローカルDocker環境(MacBook、home.docker.internal経由の内向き構成)ではこれらが用意されていない前提で、実現性上のハードルを具体的に列挙する
3. 実装しない場合の代替案(既存の定期ポーリング間隔をさらに短縮する、Task 2で検討した独立Event/Alert画面で近い体験を代替する等)を提示する
4. 結論(実現性が低い場合はその理由、実現性がある場合は必要な構成)を`instructions/13_findings.md`に記録する。**このタスクでは実装は行わない**(コードは変更しない)
