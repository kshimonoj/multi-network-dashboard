## 1. Task 1: 原因調査

### 1-1. 主因 — プロンプトに埋め込まれた例文の流用(確定)

`plugins/coach/prompt.ts` の `HINT_RULES` は、hintLevel ごとの「出し方」を日英で持っている。
65 番の実装では level 1 の説明がこうなっていた:

```
1: "見るべき観点を 1 つだけ示す。範囲は絞らない。例:「電波側と有線側、どっちの話だと思う?」",
```

`data/coach/sessions.jsonl` を走査すると、**hintLevel=1 で rogue AP を扱った 2 セッションの
両方**が、この例文をほぼそのまま本文にしていた:

- 「rogue APが出たら、まず「電波の話」と「有線の話」を切り分けるのが第一歩です。…」
- 「無線(SSID・電波・APの検知情報)の話なのか、それとも有線(スイッチやポートの状態)の話なのか——」

rogue AP は定義上、AP が電波を検知して上げる事象なので、「有線側の話でもありうる」は成立しない。
**誤った前提は教材からではなく、プロンプト自身から来ていた。**

#### A/B による因果の確認

例文だけを話題非依存の一文へ差し替え、**他は一切変えずに**同じ質問・同じ教材で
3 回ずつ実行した(モデル sonnet、hintLevel=1 固定):

| | 「有線」を含む回答 |
|---|---|
| A(現行: 例文あり) | **3 回中 2 回** |
| B(例文を差し替え) | **3 回中 0 回** |

B 側の 3 回はいずれも「rogue の判定基準は何か」「1 台か複数台か」「検知情報に何が出ているか」と、
教材の内容に沿った問いになった。**例文が原因であることは再現で確認できた。**

これは 30 番(モデルが `[SKIP]` を無言省略した件)と同じ構造の失敗にあたる。
プロンプトに書いた具体例は、指示ではなく**出力の雛形**として使われる。

### 1-2. 仮説1(ライブ情報の欠如)への結論 — 主因ではない

rogue AP の質問(`GET /api/coach/materials`)で実際に当たった教材:

| 層 | 件数 | score |
|---|---:|---|
| 承認済みナレッジ | 3 | 0.553 / 0.537 / 0.530 |
| 調査履歴 | 2 | 0.810 / 0.378 |

3 件のナレッジはいずれも **rogue AP 専用の承認済み知見**で、タイトルの時点で
「正規 SSID 一覧との照合」「RSSI による至近距離判定」「近隣他社機器との切り分け」を持っている。
つまり **Insight Agent が返した回答と同じ骨格が、静的な教材の中に既にあった。**

「元にした記録が 5 件ある」の中身も確認したが、rogue AP と無関係な低関連度の記録は混ざっていない
(全 5 件が rogue AP / alert-triage の話題キーで門を通っている)。

→ **材料不足が原因ではない。** 材料があるのに使わず、プロンプトの例文を再生産していた。
ライブ層の追加は「この誤答を直すため」ではなく、ユーザー決定どおり
**根拠の厚みと鮮度を上げるため**の施策として位置づけるのが正確。

### 1-3. 仮説2(履歴しきい値 0.05)への結論 — この事例では無関係。ただし別の副作用あり

rogue AP の質問で当たった履歴は 0.356 / 0.378 / 0.810 で、0.05 の床は判定に一切関与していない
(履歴層は「話題キーの一致」が必須の門で、0.05 は順位付けの床でしかない。65 番の設計どおり)。

一方で、**同じセッションの 3 ターン目**では実際に低スコアの履歴だけが残っていた:

```
Q: やっぱり分からないです。近くの他社のAPかもしれない?
   topicKeys=["ap-offline"]  materials=history 0.065 / 0.076 / 0.071
```

これは 0.05 の床が原因ではなく、**話題キーが `ap-offline` 1 個に痩せたこと**が原因
(次項)。しきい値そのものは変更していない。

### 1-4. 仮説3(ガードレールの肥大)への結論 — 否。ただし 1 文だけ事実と食い違っていた

66・67 番のガードレールを含めた実測サイズ(日本語 / 素材ブロックを除く system prompt):

| hintLevel | 68 番より前 | 68 番の変更後(ライブ無し / 有り) |
|---|---:|---:|
| 0 | 1,763 文字 | 2,263 / 2,680 |
| 1 | 1,757 文字 | 2,439 / 2,856 |
| 2 | 1,759 文字 | 2,270 / 2,687 |
| 3 | 1,869 文字 | 2,369 / 2,786 |

いずれも 2 千文字前後で、**長さで推論を圧迫する規模ではない**(比較: `APP_UI_RULES` 単体は
日英合わせて 2,053 文字のソースだが、実際にプロンプトへ載るのは片方のみ)。
66・67 番のガードレール(自アプリ UI 言及の禁止・hintLevel の強制・発話分類)は、
どれも「モデルに判断させない」方向の規則で、内容の推論を狭めるものではなかった。

**ただし 1 文だけ、ライブ層の追加によって事実と食い違うものがあった:**

```
- **現在のネットワークの状態は語らない。** あなたはライブデータを持っていない。
```

ライブ確認をしたターンではこれが嘘になるので、`hasLive` で切り替える形に変更した(§3-2)。

### 1-5. 副次的な発見 — 話題キーの写し方が弱点プロファイルを汚染していた

`materials.ts` の `JA_SYNONYMS` に次の行がある:

```ts
[/ap\b|アクセスポイント/i, ["ap-offline"]],
```

「AP」という語に対して `ap-offline`(= AP が落ちている、という**特定の事象**のタグ)を割り当てている。
このため **AP に言及する質問はすべて `ap-offline` を背負う**。実測:

```
rogue AP のアラートが出てるんですが… → topicKeys = [rogue-ap, alert-triage, ap-offline]
```

`GET /api/coach/weakness` の実測では `ap-offline` と `alert-triage` が弱点判定(isWeak=true)されており、
その結果 `hint.ts` の

```ts
const base: HintLevel = weakTopic ? 1 : 0;
```

が効いて、**rogue AP の 1 ターン目が hintLevel 0 ではなく 1 から始まっていた。**
つまり「弱点タグでは 1 段目から始める」という 64 番の良い設計が、
汚染されたタグ経由で「1 ターン目からあの例文を踏ませる」経路になっていた。

例文を撤去したので誤答の再生産は止まったが、**タグの写し方自体はこの番号では直していない**
(`JA_SYNONYMS` は履歴層の必須の門にも使われており、変えると 65 番で実測した
「無関係な質問 → 履歴 0 件」の結果を取り直す必要がある)。§6 に持ち越す。

### 1-6. 他の話題での「もっともらしい誤り」の探索

`data/coach/sessions.jsonl`(全 41 スナップショット / 実セッション 5 件)を走査した範囲では、
**同種の「技術的に成立しない二択」は rogue AP の 2 セッションだけ**だった。
WPA2/WPA3 混在の 3 ターンは、移行モード → ダウングレード強制 → WPA3 単独化という筋で
技術的に正しく、誤りは見つからなかった。

母数が小さいため「他に無い」とは言い切れない。ただし §1-1 の A/B が示すとおり、
**倒れ方の型は「材料が薄いときにプロンプト内の具体例を借りる」**であり、
例文を残しているのは level 1 のここだけだったので、既知の発生源は塞げている。

## 2. Task 2: ライブ情報ソース(MCP)の追加

新規ファイル `plugins/coach/live.ts`(約 420 行)。既存 3 層の**後ろに 4 層目**として足した。

### 2-1. 64 番の判断(「Coach は MCP を繋がない」)との関係

64 §2-1(b) は 3 つの理由で MCP を繋がないと決めていた。68 番はそれを**部分的にだけ**覆す:

| 64 番の理由 | 68 番での扱い |
|---|---|
| 役割の分離(現状は調査タブの仕事) | **維持**。ライブは「回答の根拠」であって「回答」ではない。取ってくるのは事実だけで、助言・対処手順は system prompt で明示的に禁止している |
| 速度(調査 1 回 113 秒) | **条件を変えた**。ツール呼び出し上限 8 回・タイムアウト 90 秒・健全性 probe なし。実測 13.6〜41.7 秒(壁打ち全体で 45〜60 秒) |
| 教材の再現性(昨日と今日で言うことが違う) | **受け入れた**。ただしライブを引いたターンは画面に `📡 ライブ確認` バッジが出るので、「今の値まで見た回答」と「過去の記録だけの回答」は区別できる |

### 2-2. 優先順位付けのロジック(`decideLive`)

**順序が設計そのもの。** 静的層を先に引き、その結果を見てからライブの要否を決める。

| 判定順 | コード | 意味 |
|---|---|---|
| 1 | `disabled` | 設定で無効(`liveEnabled=false`)→ 65〜67 番と完全に同じ挙動に戻る |
| 2 | `sessionCap` | このセッションのライブ上限(既定 4 回)に到達 |
| 3 | `offTopic` | **話題キーも取れず素材も 0 件** = ネットワークの話と判別できない |
| 4 | `liveIntent` | 「今 / 現在 / 出てる / 発生して / …」= 今の状態を聞いている |
| 5 | `noStatic` | 自社の記録(ナレッジ / 履歴)に当たりが無い(ルール層だけも含む) |
| 6 | `thinStatic` | 当たったが最高 score < `liveStaticFloor`(既定 0.45) |
| 7 | `staleStatic` | 当たったが最も新しいものでも `liveStaleDays`(既定 14 日)より古い |
| — | `staticEnough` | 上のどれにも当たらない = **静的層で足りている。ライブは引かない** |

`decideLive` は純粋関数なので、判定表を単体で実測した:

```
静的が厚くて新しい     use=false staticEnough {"score":0.55}
静的が厚いが古い       use=true  staleStatic  {"days":40,"limit":14}
静的が薄い            use=true  thinStatic   {"score":0.2,"floor":0.45}
ルールだけ当たった      use=true  noStatic
話題キーだけで素材ゼロ   use=true  noStatic
分野不明              use=false offTopic
今の状態を聞いている     use=true  liveIntent
```

`liveStaticFloor=0.45` は実測から決めた。rogue AP の質問はナレッジ最高 0.553(= 厚い側)、
「スイッチが落ちたときは」は 0.254(= 薄い側)で、0.45 はこの 2 群のあいだにある。

**`offTopic` の門は後から足した安全策。** 最初は `noStatic` だけだったが、
「有給休暇の申請方法」のような**ネットワークと無関係な質問でも素材 0 件 → ライブ発火**となり、
Central のレート制限を無駄に消費することが分かったため、
「話題キーも素材も 0 なら MCP を叩かない」を先に置いた(実測で `offTopic` に落ちることを確認)。

### 2-3. ソクラテス式の維持 — 前提 / 具体値の分離

ライブの回答をそのまま渡すと、hintLevel 0〜2 でも実測値が全部読めてしまい、
「答えは載せるのではなく渡さない」(65 番)の設計が崩れる。そこで**ライブ側にも同じ分離を作った**。

ライブ用 system prompt が出力を 2 ブロックに強制する(**言語非依存の機械可読マーカー**。CLAUDE.md 第 3 項):

```
[LIVE:premise]   … 事象がどの領域の話か / 対象の広さ / 件数。固有名詞・実測値・原因の見立ては書かない
[LIVE:detail]    … 実測値と固有名詞そのまま
```

- `premise` → `CoachMaterial.body`。**hintLevel に関係なく常に渡す**(前提を間違えないため)
- `detail` → `CoachMaterial.answerBody`。**hintLevel 3 でのみ渡す**(既存の `buildMaterialBlock` にそのまま乗る)

実測の分解結果(伏字後):

```
hadMarkers true
--- PREMISE ---
組織全体 13 サイトのうちアラートが立っているのは 1 サイトのみ。無線 AP のシステム系アラートで、
Rogue AP(不正 AP 検知)カテゴリのアラートは今回取得した範囲では確認できていません。
--- DETAIL ---
central_get_summary: <サイトA>(site_id: <伏字>)のみ total_alerts=1, critical_alerts=1 …
- "AP Offline"(severity: Critical, …, device: <機器A>)
- "Config Out of Sync"(severity: Critical, …, device: <機器A>)
```

**マーカーが出なかった場合は安全側へ倒す**: 本文をすべて `detail` 扱い(= hintLevel 3 まで出さない)にし、
`premise` は**モデルの文章を読まずに**組み立てられる情報(叩いたツールの数・プラットフォーム名)だけで作る。
「前提のつもりで答えを載せてしまう」方向の事故を構造的に起こさないため。

### 2-4. レート制限・タイムアウトへの配慮

Central API は秒 10 回程度・**アカウント全体で共有**。「1 往復ごとに Central を叩く Coach」を
作らないことが前提になる。5 段構えにした(効き目の大きい順):

| 機構 | 既定 | 効果 |
|---|---|---|
| **キャッシュ** | 300 秒 / `lang + platforms + 話題キー` | 同じ話題で壁打ちを続けても MCP 問い合わせは **1 回**。実測で 2〜3 ターン目が `fromCache:true` |
| **分野の門** | — | ネットワークと判別できない質問では叩かない(`offTopic`) |
| **同時実行 1 本** | 固定(env で変更不可) | 同じキーなら相乗り、違うキーなら**待たせずに見送る**(`busy`)。実測で確認 |
| **最小間隔** | 15 秒 | 直前の実行開始からこれ未満なら見送る(`rateLimited`)。実測で確認 |
| **セッション上限** | 4 回 | キャッシュヒットは数えない(`sessionCap`)。実測で確認 |

タイムアウト(62 番で判明した `DEFAULT_TIMEOUT_MS=240000` への配慮):
`runClaudeWithMcp` の `timeoutMs` に **`liveTimeoutMs`(既定 90 秒)を明示的に渡す**ので、
Coach のライブ問い合わせが 240 秒待つことはない。加えて `checkHealth:false` にしてある
(健全性 probe は「1 度も呼ばれなかったサーバー」に追加の往復を生む。ライブは失敗しても
静的層で成立するので、対話の途中で追加コストを払う理由がない)。

実測の所要時間: 13.6 / 18.4 / 23.3 / 35.7 / 37.5 / 38.6 / 40.2 / 41.7 秒(8 回)。
壁打ち 1 往復の全体は 45〜60 秒。

**読み取り専用の担保**: `--allowedTools` はサーバー単位のワイルドカードなので書き込み系も通る。
`runClaudeWithMcp` に `disallowedTools` を追加し(既存呼び出しへの影響なし)、Coach からは
`central_bounce_port` / `central_run_network_test` / `central_run_show_commands` を締め出した。

### 2-5. クイズモードは対象外(判断)

指示 Task 2-4 の「クイズは過去事例からの出題なのでライブ不要」はそのとおりで、**ライブを繋いでいない**。

- 理由: クイズの正解は素材に紐づく。「今この瞬間の状態」を正解にすると**翌日には正解が変わる**
- 実装上も、クイズの素材プール(`quiz.ts` の `quizPool`)は knowledge / history / rule から作られ、
  `decideLive` を通る経路が無い
- 本番で出題 → 採点まで確認し、MCP 呼び出しが 0 回・所要 5.8 秒であることを確認した

## 3. Task 3: ガードレール・プロンプトの見直し

§1-4 のとおり**肥大は主因ではなかった**ので、66・67 番のガードレールは削っていない。
代わりに、§1-1 で特定した発生源とその周辺だけを直した。

### 3-1. 例文の撤去と、倒れる方向の指定

- `HINT_RULES` の level 1 / 2 から**具体例を撤去**し、「観点は今回の話題と教材から選ぶ」だけを残した
- level 1 に「**問いは相手がその場で確かめられる具体的な事実に向ける**。
  分類を当てさせる問い(「無線と有線どっち?」「どの管理システムの話?」)にしない」を追加
- 新しい規則ブロック `NO_FALSE_PREMISE_RULES` を追加。禁止だけを書くと逃げ場が無くなって
  かえって作文が増えるので、**代わりに何をすればよいか**(相手の現在地を聞く)を必ず添えている

**実装中に踏んだ回帰と、その修正:** この「材料が足りないときは現在地を聞く」を無条件に書いたところ、
**hintLevel 3(強制開示)のターンでモデルが問い返しに逃げた**(64・66・67 番が保証していた
「必ず開示に到達する」が空振りした)。「ただしレベル 3 ではこの逃げ道を使わない」を明記して解消。
修正後は同じ経路で開示が行われることを再実行で確認済み(§4-1)。

### 3-2. ライブの有無で切り替える規則

- 絶対規則の「あなたはライブデータを持っていない」を `hasLive` で分岐
  (ライブ有り: 「現在の状態はライブ確認の事実だけを根拠にする」)
- `LIVE_RULES` ブロックを追加。要点は 3 つ:
  - 事実は**前提を正しくするために使う。そのまま読み上げない**(読み上げると調査タブの劣化版になる)
  - **ライブが「無い」と言っているものを「ある」ものとして語らない。**
    相手の申告とライブ結果の食い違い自体が最も価値のある事実
  - 問いを「どちらのベンダー / 管理システムの話か」に向けない(ライブで既に分かっている)
- マーカー規則に `[SRC:live:<id>]` を追加(`markers.ts` の検出正規表現も更新)

### 3-3. 実装中に踏んだもう 1 つの回帰 — キャッシュの言語非対応

最初の実装はキャッシュキーに言語を含めていなかった。その結果、**ja で取った digest が en のターンに配られ、
モデルが日本語の要約を読み違えて「rogue AP アラートが出ている」と事実と逆のことを書いた**
(ライブの premise は「見つからなかった」と言っていた)。
キャッシュキーに `lang` を追加して解消。増えるのは TTL 内で最大 2 本まで。
修正後の英語ターンは、ライブの事実と矛盾しない問いを返すことを確認済み。

### 3-4. しきい値は変更していない

`threshold=0.15` / `historyThreshold=0.05` は据え置き。§1-3 のとおりこの事例には関与しておらず、
「静的が薄いならライブへ回す」は**別の数値(`liveStaticFloor=0.45`)**で表現した。
既存のしきい値を動かすと 65 番で実測した履歴層の判別結果(無関係な質問 → 0 件)を
取り直す必要があるため、そちらには触れないほうが安い。

## 6. 未確認・次回に持ち越した事項

1. **`JA_SYNONYMS` の `ap` → `ap-offline` の写し方**(§1-5)。AP に触れる質問すべてが
   「AP がオフライン」というタグを背負い、弱点プロファイルを汚染している。
   直すべきだが、この表は**履歴層の必須の門**でもあるため、変更すると 65 番で実測した
   判別結果(無関係な質問 → 履歴 0 件)の取り直しが要る。単独の作業にするのが安い。
2. **話題キーの語彙が薄い領域**。「PoE の給電が足りているか」は話題キーも素材も取れず
   `offTopic` に落ちる(= ライブも引かない)。ネットワークの質問なのに門で止まる例が他にもあるはず。
   §6-1 と同じ表を触る作業なので、まとめて扱うのがよい。
3. **`staleStatic` の実データでの発火**。判定表(純粋関数)では確認したが、
   現在のナレッジ・履歴はすべて 14 日以内なので**実データでは一度も発火していない**。
4. **ライブ失敗時(タイムアウト・認証切れ)の挙動**。コード上は「静的層だけで続行 + `reasonCode:"failed"`」だが、
   実際に MCP を落として確かめてはいない。
5. **`liveStaticFloor=0.45` の妥当性**。2 群(0.553 / 0.254)のあいだに置いただけで、
   境界付近(0.4〜0.5)の質問での挙動は測っていない。運用しながら調整する前提。
6. **hintLevel 1 での過剰開示**。WPA2/WPA3 の質問では、`answerBody` を渡していないのに
   モデルがナレッジのタイトル + 一般知識からダウングレード攻撃の説明まで書いた。
   68 番で入れた変更とは無関係(65 番からの挙動)だが、ソクラテス式としては前のめり。
7. **並列利用時のレート制限**。同時実行 1 本・最小間隔 15 秒は Coach 内部の話で、
   **定期実行の調査・Webhook の自動事前調査と競合したときの合計流量**は測っていない。
   Coach 側は最大でも 15 秒に 1 回なので支配的ではないはずだが、実測はしていない。
