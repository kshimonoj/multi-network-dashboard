# 64: Coachタブ — ソース設計・ソクラテス式応答の設計(実装はまだ行わない)

## 背景・目的

- ジュニアなネットワーク運用者を育成するためのCoach機能を新設したい
- ソース(回答根拠)は、自社のナレッジ(Knowledgeタブの承認済み知見)・過去のネットワーク調査履歴(Network Investigationの履歴)・ベンダーのベストプラクティス(Best Practiceタブのルール)の3つ。優先度は**自社のナレッジ/調査履歴を最優先**とし、ベンダーのベストプラクティスは補助的に使う
- 壁打ち(ジュニアが自由に質問する)に加えて、**Coach側から自社の過去事例をモチーフにした問題(クイズ)を出題する能動的な学習モードも欲しい**
- 回答は答えをそのまま返さず、気づきを与えて育てる形にする(ソクラテス式・ヒント中心)。これはInsight Agent(即答・診断が目的)とは設計思想が正反対のため、**新規独立タブ「Coach」として完全に分ける**

今回はいきなり実装せず、49番・57番の進め方に倣い、**ソース設計とソクラテス式応答の設計方針の確定まで**を行う。

## タスク

### Task 1: ソースの整理・設計

1. Knowledgeタブに蓄積されている承認済み知見の構造(参照回数・最終参照日時等を含む既存スキーマ)を確認し、Coachがどのフィールドを使えるか整理する
2. Network Investigationの過去の調査履歴について、どこにどういう形式で保存されているか(日次/週次/月次のレポートとの関係も含む)を確認し、Coachが「教材」として使える形かどうかを検討する
3. Best Practiceのルール(29 ID)について、Coachが「一般知識の補助」としてどう参照するかを検討する(診断結果そのものではなく、ルールのtitle/desc/referencesが教材向きかを確認する)
4. 3つのソースを横断して「その会社ならではの事象」を抽出する際の優先順位付けロジックの方針を設計する(自社ナレッジ最優先、無ければ調査履歴、それでも無ければベストプラクティスの一般知識、という段階的フォールバックのイメージ)

### Task 2: ソクラテス式応答の設計

1. 「答えをそのまま返さず気づきを与える」ための system prompt の設計方針を検討する(既存のInsight Agent/Best Practiceの所見生成プロンプトとは別物として設計する)
2. ジュニアの質問のレベル(初歩的〜踏み込んだ質問まで)に応じて、ヒントの出し方をどう調整するかの方針を検討する
3. 「答えを出し渋りすぎて学習効果が下がる」ことを避けるためのバランス(例: 一定回数やり取りしても核心に近づけない場合は答えに近づける、等)の設計方針を検討する
4. 壁打ちの会話履歴をどう保持するか(セッション単位か、ジュニアごとの継続的な学習履歴を残すか)の方針を検討する

### Task 3: 能動的な学習モード(クイズ出題)の設計

1. 自社の過去事例(ナレッジ・調査履歴)からクイズを自動生成する仕組みの設計方針を検討する(元ネタの選び方、出題形式、難易度調整等)
2. 出題→回答→フィードバック(ここもソクラテス式で、正解をそのまま言わずヒントを与える形にできるか)の流れを設計する
3. 同じ事例から繰り返し出題されないようにする工夫(ナレッジの参照回数記録の仕組みが応用できないか)を検討する

### Task 4: タブの位置付け・画面構成の設計方針(実装はしない)

1. 新規独立タブ「Coach」の基本構成(壁打ちチャット画面+クイズモード切替等)の設計方針を記載する
2. 既存タブとの導線(例: ナレッジタブから「この事例で学ぶ」的なリンクがあると良いか等)を検討する
3. **UIトーンの制約(重要)**: 既存タブ(Global Overview・Best Practice等)は業務システム然としたプロフェッショナルな見た目(青・紫中心)だが、Coachタブはジュニア運用者向けであるため、素人でも馴染みやすい親しみやすいUIにする。既存タブの配色(Blue/Purple)は避け、暖色系(アンバー等)+丸みのあるチャットバブル+アイコンでキャラクター性を出す方向性。文言もカジュアルなトーンにする。この方向性はユーザーとチャットで既に合意済みなので、大きく外れない範囲で具体化してよい
4. ワイヤーフレームレベルの設計方針の記載に留め、実装は次回以降に回す

### Task 5: 追加機能の設計方針

1. **エスカレーション導線**: 壁打ち中に「もう答えを教えて」のような形で、ソクラテス式のヒント出しから直接回答(Insight Agent相当の即答)に切り替えられる導線を設計する。実際の障害対応中にヒントで粘りすぎることの危険性を避けるための機能
2. **弱点の記録**: ジュニアがどのあたりでつまずいたか(質問内容・ヒントを何度要求したか等)を記録する仕組みを設計する。記録した弱点情報を、次回以降のクイズ出題やヒントの出し方(同じ弱点を繰り返し扱う等)にどう反映するかの方針も検討する。永続化方式は既存プロジェクトのdata/配置慣習に合わせる
3. **根拠へのリンク提示**: ヒントの元になったナレッジ・過去の調査結果へのリンクを、壁打ちの回答に添える設計を検討する(53番のルールリファレンスの展開表示パターンが参考になる可能性がある)
