# 55: 49〜54番の変更をコミット・GitHubへpush

## 背景

- 49〜54番でベストプラクティス診断タブ一式(調査・ルール設計・PMF出力形式確定・実行エンジン/API・タブUI・展開表示/ルールリファレンス・Mist確認・本番反映)を実装してきたが、これまで一貫して「git操作は行わない」という制約のもとで進めてきたため、まだ一度もコミットしていない
- リポジトリはGitHub公開済み(https://github.com/kshimonoj/multi-network-dashboard)。初回公開時は実データ全走査・伏字化のセキュリティ監査を経てpushしている経緯があるため、今回も同水準の確認をしてからpushすること
- 本番コンテナ(8092)は既にrebuild済みで動作確認済み(54番)。コミット対象はそれ以前のワーキングツリーの変更一式

## タスク

### Task 1: 変更内容の棚卸し

1. `git status`で49〜54番による変更ファイル一覧を確認する(想定: `plugins/best-practice/`一式、`src/main.tsx`、`src/i18n/ja.json`/`en.json`、`server/index.ts`等)
2. `instructions/`配下に49〜54番の指示ファイル・findingsファイルが存在する場合、これまでの他の番号(41〜48番等)がリポジトリに含まれているかどうか(`.gitignore`の扱い)を確認し、既存の慣習に合わせる(含めるなら含める、除外されているなら合わせて除外する)

### Task 2: コミット前のセキュリティ監査

1. 変更差分(`git diff`)全体を対象に、以下が含まれていないことを確認する:
   - 実際のSSID名・サイト名・デバイスシリアル
   - APIトークン・パスワード・RADIUS共有シークレット等の秘匿情報
   - 顧客名・組織名等、公開を意図していない固有名詞
2. 特に51番で扱った`show running-config`関連のテストデータ・ログ出力・findingsファイルに実データが紛れ込んでいないかを重点的に確認する(51番の完了報告で「機密情報0件」は確認済みだが、コミット対象ファイル全体としての再確認)
3. 問題があれば伏字化・除外してから次に進む

### Task 3: コミット

1. 論理的にまとまった単位でコミットを分ける(例: 実行エンジン/API、UI、i18n、ドキュメントなど。1コミットに全部まとめても良いが、後から追いやすい粒度を優先する)
2. コミットメッセージは何を実装したか(ベストプラクティス診断: ルール設計・実装・UI・Mist対応)が分かる内容にする

### Task 4: push

1. `git push`でGitHubリポジトリに反映する
2. push後、GitHub上でファイル一覧・差分を確認し、意図しないファイル(機密情報や個人環境固有のパス等)が含まれていないことを再確認する

## 制約

- pushする前に必ずTask 2のセキュリティ監査を完了させること。監査で疑わしい内容が見つかった場合は、pushを止めて内容を報告し指示を仰ぐこと
- 本番のSSID・WLAN設定の変更は行わない(このタスクの範囲外)

## 完了報告

verified-report形式で報告すること。特に:

- コミットしたファイル一覧とコミットメッセージ
- セキュリティ監査の実施内容と結果(何を確認して問題なしと判断したか)
- pushが成功したことの確認(GitHub上での確認結果含む)

---
**推奨モデル: Sonnet**(既存の公開手順に沿った機械的な作業のため。ただしセキュリティ監査で疑わしい内容が見つかった場合の判断が必要になれば、その時点でOpusへの切り替えを検討)
