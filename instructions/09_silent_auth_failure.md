# 09: MCP認証失敗のサイレント埋没問題への対応(multi-network-dashboard)

## 背景(08番からの引き継ぎ)

MCPサーバー(central-mcp/mist-cloud)自体の認証(Bearerトークン等)が無効な場合、claude CLIのハンドシェイク段階でそのサーバーのツールが1つも登録されない。この状態でもclaude CLIの実行自体は`is_error: false`(成功)として完了し、モデルが地の文で「ツールが見つかりません」と書くだけで終わる。結果として、画面には赤い「失敗」表示が一切出ず、ユーザーは認証切れに気づけない。

Central APIのトークンは約2時間で失効する(05番で判明済み)ため、この問題は実運用で実際に発生し得る。

## タスク

### Task 1: ハンドシェイク失敗を検出する方法の調査

1. claude CLIの`--print --output-format stream-json --verbose`が返すイベント列を確認し、起動直後の`system`(init)イベントに、各MCPサーバーの接続状態(接続成功/失敗、登録されたツール数等)が含まれているか確認する。含まれていれば、そのイベントを使って検出できる
2. 含まれていない場合、代替手段として以下を検討する:
   - 事前にサイトに応じて絞り込んだMCPサーバー一覧(narrowing済みconfig)と、実際にその実行で呼び出された(または呼び出そうとして失敗した)MCPサーバー名を突き合わせ、「呼ばれるべきだったサーバーが一度も登場していない」場合に警告扱いにする
   - 実行前に軽量なヘルスチェック的な呼び出し(例: 各MCPサーバーへの`initialize`相当)を行い、ツールが1件も返らない場合はその場でエラーとして扱う
3. 調査結果と採用する方式を`instructions/09_findings.md`に記録する

### Task 2: 検出結果をUIに反映する

1. Task 1で採用した方式を実装し、「ツール呼び出しが0件のまま完了した」実行のうち、想定されるMCPサーバーが実際には使われなかったケースを検出したら、通常の「完了」ではなく「一部のMCPサーバーに接続できませんでした(認証切れの可能性)」等の警告表示にする
2. どのサーバー(central-mcp/mist-cloud)が接続できなかったかを具体的に示す
3. 誤検知(本当にツールを使う必要がない質問だった場合等)を避けるため、慎重に条件を設計する。判断が難しい場合は、断定的な「失敗」ではなく「確認が必要」程度の警告レベルに留めてもよい

### Task 3: 動作確認

1. 意図的にMCPサーバーの認証情報を無効化した状態(本番の`.env`/`.claude.json`は変更しない、08番と同様の手法で壊したコピーを使う)で実際に再現させ、警告表示が正しく出ることを確認する
2. 正常時(認証情報が有効)には誤って警告が出ないことを確認する
3. 検証後は必ず本来の認証情報に戻す
4. `docker compose up -d --build`で反映し、`/health`と実画面を確認する

## 完了報告

verified-report形式で報告すること。特に:

- 採用した検出方式とその根拠
- 意図的な認証無効化での再現・警告表示の確認結果
- 正常時に誤検知しないことの確認結果
- 検証後の認証情報復元の確認
- `docker compose up -d --build`後の反映確認結果
