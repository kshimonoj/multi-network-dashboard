## 1. Task 1: 現状の保存方式(42 番より前)

### 1-1. 単一のローリングバッファだった

`plugins/webhook-feed/poller.ts` の保存は **feed.json 1 枚**で、日付では一切分かれていなかった。

```ts
const MAX_ITEMS = Math.max(200, Number(process.env.WEBHOOK_FEED_MAX_ITEMS ?? 3000));

function sortItems(): void {
  items.sort(/* 受信時刻の新しい順 */);
  if (items.length > MAX_ITEMS) items = items.slice(0, MAX_ITEMS);  // ← ここで古い行が消える
}
```

- `sortItems()` は毎回の refresh で呼ばれ、**全ソース合計**が `MAX_ITEMS` を超えると
  受信時刻の古いものから捨てられる。ソース別・日付別の枠は無い。
- `persistFeed()` はこの切り詰め後の `items` をそのまま `data/webhook-feed/feed.json` に書く。
  つまり **メモリから落ちた時点でディスクからも消える**。復元経路は無い。
- `WEBHOOK_FEED_MAX_ITEMS` は `docker-compose.yml` に**書かれていなかった**ため、
  実際に効いていたのはコード既定値の 3000。

### 1-2. 実測(42 番の作業を始めた時点の feed.json)

| 項目 | 値 |
|---|---|
| 保持件数 | 3000 件(= 上限ちょうど。**溢れている状態**) |
| 内訳 | 2026-07-31 が 2685 件 / 2026-08-01 が 311 件 / 壊れた eventAt が 4 件 |
| ファイルサイズ | 4.9MB(インデント付き JSON) |
| シート側の累計行 | MistLog だけで 21,334 行(`state.json` の `lastRows`) |

2 日ぶんで既に上限に張り付いており、**2026-07-30 以前は 1 件も残っていない**。
41 番の実測(Mist だけで 1 日 2949 件)と合わせると、**1 日ぶんですら収まらない日がある**。

### 1-3. 日次レポート(41)への影響

41 番の `collectWebhook()` は `getCachedFeed().items` を日付で絞っていたので、
上限から溢れた日は必ず 0 件になった。41 番はこれを見越して
「手元の最古行がその日の終端より新しければ `available:false`」という分岐を入れてあり、
**0 件と未計測は区別できていた**。ただし区別できるだけで、集計そのものは不可能だった。

さらに、上限に張り付いている日(= 最古の日)は
**「一部だけ残っている」状態なのに `available:true` として集計されてしまう**。
41 番の 2026-07-31 = 2695 件は実際の発生件数ではなく「上限に切られた後の残骸」だった。
これは 41 番の findings には書かれていない、より深い問題。

### 1-4. 41 番の記載に対する訂正

41 番 `2-2` の「保持上限(`WEBHOOK_FEED_MAX_ITEMS` 既定 3000)より古い日は必ず 0 件になる」は正しいが、
**上限に張り付いている日の件数も過少である**点が抜けている。42 番で両方を解消した。

## 2. Task 2: 新しい保存方式

### 2-1. 「見せる量」と「保存する量」を別物として分けた

```
保存(正本)  data/webhook-feed/daily/YYYY-MM-DD.jsonl   1 行 1 イベント・追記のみ・件数上限なし
             data/webhook-feed/archive-meta.json        保存開始日 / 移行の記録 / 日別件数
表示(派生)  data/webhook-feed/feed.json + メモリ       直近 N 件(既定 3000)のキャッシュ
```

- **保存に件数上限は無い**。制限は日数(Retention)だけ。1 日に何件来てもその日のファイルは
  ファイルごと残るので、他の日を押し出すことがない。
- **表示は今までどおり直近 N 件**。`WEBHOOK_FEED_MAX_ITEMS` は残したが、
  意味を「見せる量の上限」に限定し、変数名も `VIEW_MAX_ITEMS` に改めた。
  ここから溢れた行はアーカイブに残るのでデータは失われない。

| ファイル | 変更内容 |
|---|---|
| `plugins/webhook-feed/archive.ts` | **新規**。追記 / 読み出し / 移行 / Retention / 集計 |
| `plugins/webhook-feed/poller.ts` | 切り詰め前にアーカイブへ追記。Retention 設定・集計の公開 |
| `plugins/webhook-feed/api.ts` | 起動時の初期化に移行を追加。`GET /archive`、`POST /settings` の拡張 |
| `plugins/webhook-feed/feed-types.ts` / `view/types.ts` | `storage` / Retention 設定の型 |
| `plugins/webhook-feed/view/*` | フッタに「保存」行(保持日数の選択 + 保存/表示の内訳) |
| `plugins/reports/collect.ts` | Webhook の集計元を**メモリからアーカイブへ**変更 |
| `plugins/reports/types.ts` / `analyze.ts` | `source` / `partial` を追加し、LLM にも渡す |
| `src/i18n/ja.json` / `en.json` | フッタの文言(日英同時に追加。キー数 657 で一致を確認) |
| `Dockerfile` / `docker-compose.yml` | `daily/` の作成、`WEBHOOK_FEED_ARCHIVE_RETENTION_DAYS` |

### 2-2. 1 日の境界はレポート側と共有する

日付キーは `plugins/reports/time.ts` の `dateKeyOf()`(コンテナのローカル TZ)を
**そのまま import して使う**。ファイル名の日付とレポートの集計区間が同じ定義で切られていないと、
境界付近の行が「どのファイルにも入らない」「二重に数えられる」ことになるため。

### 2-3. 行に何を書くか — auto / siteContext は書かない

アーカイブに書くのは取り込み時点の `WebhookFeedItem` から
`auto`(自動事前調査の結果)と `siteContext`(先読み)を落としたもの。

この 2 つは後から非同期に付く上に何度も更新される。書き戻すと jsonl が
「追記のみ」でなくなり、行の書き換え = ファイル全体の再書き込みが必要になる。
一方でこの 2 つは `state.json` が `alertKey` をキーに正本を持っており、
既存コードが読み込み時に貼り直している。**アーカイブは「そのとき何を受信したか」に徹する**。

### 2-4. 重複を作らない

`id`(= `source#rowIndex`)と `alertKey` を組にしたキーで判定する。
`id` だけにしなかったのは、シートがクリアされた(resync)ときに同じ行番号へ別のイベントが
入り得るため。判定用のキー集合は日ごとに遅延ロードして最大 5 日ぶんキャッシュする。

### 2-5. 壊れた eventAt への対処(実データで見つかった)

Mist の NAC 系イベントに、上流で単位を取り違えた `+058549-08-30T08:22:30.000Z` という
**年が 5 桁の eventAt** が実在した(4 件)。素直に日付キーにすると
`58549-08-30.jsonl` というファイルができ、`^\d{4}-\d{2}-\d{2}$` に一致しないので
**一覧にも Retention にも乗らないゴミが静かに溜まる**。

そこで `isSaneTime()`(2000-01-01 〜 現在 +2 日)を設け、
`eventAt` → `receivedAt` → 取り込み時刻 の順に**まともな値**を採用する。
この 4 件は `receivedAt`(2026-07-31)が正しいので、正しい日に入る。

副次的に、41 番ではこの 4 件が `inWindow()` で弾かれて**どの日にも数えられていなかった**のが、
42 番では 07-31 に正しく数えられるようになった(2685 → 2689)。

### 2-6. Retention(保存自体の上限)

- 設定名 `archiveRetentionDays`。既定 90 日、`0 = 無期限`。選択肢は 0 / 30 / 90 / 180 / 365。
- 保存先は Webhook ログ既存の `data/webhook-feed/settings.json`(ポーリング間隔と同居)。
  画面のフッタ・`POST /settings` から変更でき、短くするとその場で古い日のファイルを消す。
- 「保持 N 日」= **今日を含む直近 N 日を残す**(41 番のレポート Retention と同じ定義)。
- 定期実行は 1 時間に 1 回まで(日単位の判定なので毎巡やる意味が無い)。

### 2-7. レポート側の読み替え

`collectWebhook()` はアーカイブから対象日のファイルを直接読む。判定は 3 通り:

| 状況 | 結果 |
|---|---|
| ファイルがある | `available:true` / `source:"archive"` / 件数はファイルの行数そのもの |
| ファイルが無く、保存開始日以降 | `available:true` / **0 件で確定**(1 件も受信しなかった日) |
| ファイルが無く、保存開始日より前 | `available:false` + 「42 番より前は上限で失われており復元できません」 |

移行日(= 旧 feed.json の最古日)は `partial:true` を立て、
「0:00 からではなく途中からの記録」であることを注記する(2-1-3 で書いた過少計上への手当て)。
`source` / `partial` / `note` は `analyze.ts` から **LLM にも渡す**。
件数の読み方が変わるのに数字だけ渡すと誤読されるため。

アーカイブがまだ初期化されていない場合(初回起動直後など)は、
旧経路(メモリを期間で絞る)にフォールバックし `source:"memory"` を立てる。

## 3. Task 3: 移行

起動時(`initWebhookFeed()`)に `archive-meta.json` が無ければ 1 度だけ、
`feed.json` から読み戻した全件を日別ファイルへ振り分ける。meta があれば何もしない(冪等)。

**実測(本番コンテナ)**:

```
[webhook-feed] アーカイブへ移行: 3000 行 / 2 日分 (2026-07-31 〜 2026-08-01)。
               2026-07-31 は旧方式の保持上限で途中から始まっている可能性があります。
[webhook-feed] アーカイブ: 2 日分 / 3000 件 / 3.7MB (... / 保持 90 日 / 表示は直近 3000 件)
```

| 日 | 移行件数 | 状態 |
|---|---|---|
| 2026-07-31 | 2689 | `partialDays` に登録(**1 日ぶん揃っていない**) |
| 2026-08-01 | 311 | 完全 |
| 2026-07-30 以前 | — | **復元不能**。旧方式の上限で既に失われている |

> **欠落済み過去分について**: 2026-07-30 以前の Webhook ログは、42 番の作業を始めた時点で
> 既に feed.json から溢れて存在しない。Google スプレッドシート側には残っているが、
> `state.json` の `lastRows` が読み取り済みの位置を指しているため、通常の差分取得では戻らない。
> 42 番では**復元を試みていない**(シートを全件読み直す = 自動事前調査の再発火や
> API 消費を伴うため、別タスクの判断とする)。今後の日は欠落しない。

## 5. 運用上の注意

- **ディスク見積り**: 1 日 3000 件 ≒ 3.7MB。90 日 = 約 330MB。
  1 日 1 万件が続く環境では 90 日で 1GB を超えるので、その場合は保持日数を短くする。
- `WEBHOOK_FEED_MAX_ITEMS` は**表示だけ**の上限になった。小さくしても保存は減らない。
  逆に、一覧を軽くしたいときはこれを下げるのが正しい対処になった。
- 日別ファイルは追記のみなので、外部ツール(`wc -l` / `jq`)でそのまま数えられる。
