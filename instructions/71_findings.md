# 71: ナレッジの重複問題の調査・修正 — 実施結果

※ サイト名・機器名は仮名(サイトA / AP-X)に置き換えて記載する。

## Task 1: 原因調査

### 1-1. 承認済みとの比較は「行われていた」。ただし判定ではなく提案止まりだった

指示の仮説は「新規候補どうしの間でしか比較していない可能性が高い」だったが、
コードを読むと **承認済みとの比較は 46 の時点で実装されていた**(`extract.ts` の
`findSimilar(cand, approvedPool, threshold, 3)`)。

問題は比較の有無ではなく、**比較結果の扱い**だった:

| 相手 | 46 の挙動 |
|---|---|
| 未承認候補(pending)と一致度 >= 0.35 | 候補を**作らない** |
| 承認済み(approved)と一致度 >= 0.35 | 候補を**作る**。`similar` にマージ提案を添えるだけ |

つまり承認済みと重複しても pending に必ず積まれる設計だった。これが
「承認済みと同じ内容の候補が未承認リストに再浮上する」の一次要因。

### 1-2. さらに、しきい値 0.35 にほとんど届いていなかった

実データ(`data/knowledge/entries.json`: 承認済み 24 / 未承認 52)で、
未承認候補それぞれと承認済み全件の一致度を測り直した。

rogue AP 関連の未承認候補 10 件のうち、最良の承認済みエントリとの一致度が
0.35 を超えたのは **1 件だけ**(0.375)。残りは 0.245〜0.348 で、
`similar` が空のまま「まったく新規の知見」として並んでいた。

一致度の内訳(代表例):

```
0.348  P: Rogue AP検知でevil twinと外部固定機器を切り分ける判定ロジック
       A: Rogue APアラームの脅威度評価は正規SSID一覧との照合と近隣他社機器の切り分けで行う
       title=0.253 symptom=0.338 tag=0.667
0.305  P: Periodic single-AP rogue alerts from one source AP ...   ← 英語の候補
       A: Rogue APアラームの脅威度評価は ...                        ← 和文のエントリ
       title=0.127 symptom=0.221
```

### 1-3. なぜ一致度では切れないのか(しきい値調整では直らない)

同じ帯にまったく別の事象が入り込む:

| 組 | 一致度 | 実際 |
|---|---|---|
| rogue AP の切り分け手順(言い換え) | 0.245〜0.375 | 重複 |
| スイッチ全断 ⇄ 仮想ラボ一括再起動 | 0.324 | 別の事象 |
| 複数スイッチ同時オフライン(2 件) | 0.315 | 重複 |

**0.30 付近に重複と非重複が混在している**ので、1 本のしきい値では切れない。
下げれば別事象を潰し、上げれば重複を通す。理由は 2 つ:

1. 日本語は語順・助詞・言い回しの自由度が高く、同義の 2 文でも文字 bigram が重ならない。
2. `score()` が見ているのは **タイトルと症状だけ**(根本原因・対処は未使用)。

加えて **英語の候補と和文のエントリは bigram が原理的にほぼ重ならない**ため、
言語をまたぐ重複は一致度では絶対に検出できない。

改善案として IDF 重み付き bigram コサインも試したが(scratchpad で実測)、
重複 0.20〜0.26 / 別事象 0.16 前後と帯の重なりは解消しなかった。**語彙ベースの
指標では判定できない**と結論した。

### 1-4. 却下済みが比較対象に入っていなかった

`findSimilar(cand, [...pendingPool, ...keep])` は pending だけを見ていたため、
人が一度「却下」した知見も、次の調査から作り直されて戻ってきうる状態だった。

## Task 2: 修正

### 2-1. 判定を 2 段構えにした(絞り込み → LLM 判定)

| 段 | 実装 | 役割 | コスト |
|---|---|---|---|
| 絞り込み | `similarity.ts` `shortlistSimilar()` | 再現率だけを見て相手を最大 5 件に絞る | 0 |
| 判定 | `dedupe.ts` `judgeAgainstApproved()` | 同じ知見かを LLM が判定 | 相手が残った候補があるときだけ 1 回 |

- 絞り込みのしきい値は 0.15(判定用より意図的に低い)。加えて **タグを 1 個でも
  共有していれば一致度を無視して相手に含める**。タグは日英どちらのエントリでも
  英語(`rogue-ap` 等)で付くので、**言語をまたぐ唯一の橋渡し**になる。
- 判定は列挙値(`duplicate` / `related` / `new`)と参照キー(`K3`)だけを読む。
  参照キーは「その候補に提示した相手」に実在するものだけ採用する
  (CLAUDE.md「モデル出力を自然言語でパースする実装を作らない」に沿う)。
- LLM が落ちた / 応答が壊れていた場合は **46 の挙動へ縮退**(一致度 >= しきい値なら
  related = マージ提案、それ以外は new)。判定できないことを理由に候補を握り潰さない。

新規ファイル: `plugins/knowledge/dedupe.ts` / `plugins/knowledge/llm.ts`
(`llm.ts` は 46 で `extract.ts` に閉じていた claude CLI 呼び出しを共有化しただけ。挙動は不変)

### 2-2. 重複時の扱い

| 判定 | 扱い |
|---|---|
| `duplicate` | 候補を**作らない**。相手の承認済みエントリに **出典だけ**を足す(本文は不変) |
| `related` | 従来どおり候補にして `similar` にマージ提案を添える |
| `new` | 従来どおり候補にする |

出典を足すのは「この知見が今回の調査でも当てはまった」という記録で、
承認画面の出典一覧からその調査へ飛べるようになる(再確認の可視化)。
`sources` は 46 からマージで増える設計なので、既存の作法に沿っている。
本文に手を入れないので「承認は必ず人が押す」という 46 の原則は崩していない。

また **却下済み(rejected)を既出プールに追加**した。人が一度要らないと判断した
知見が黙って戻ってこないようにするため。

### 2-3. 溜まっている未承認候補の整理

`POST /api/knowledge/dedupe-pending` と、未承認タブの
「**承認済みとの重複を検出**」ボタンを追加。

- ① 検出(`pairs` なし)… 何も変えずに重複の組を一覧で返す
- ② まとめて統合(`pairs` あり)… **判定をやり直さず**、画面に出ていた組をそのまま適用

②で再判定しないのは、人が見たものと違う結果を適用しないため。
統合の中身は既存の `POST /entries/:id/merge` と同じ(相手に出典とタグを足し、
候補は消さずに `status="merged"` で残す。本文は不変)。復活も従来どおりできる。

一括却下ではなく統合にしたのは、却下だと出典が失われ「この知見が何回再確認されたか」が
残らないため。

### 2-4. 設定

`settings.dedupe` を追加(`store.ts`):

| キー | 既定 | 環境変数 |
|---|---|---|
| `llm` | true | `KNOWLEDGE_DEDUPE_LLM=0` で 46 の一致度のみの挙動へ |
| `shortlistMax` | 5 | `KNOWLEDGE_DEDUPE_SHORTLIST_MAX` |
| `suppressDuplicates` | true | `KNOWLEDGE_DEDUPE_SUPPRESS=0` で候補を作る挙動へ |

抽出ログに `duplicateApproved`(承認済みと同一で見送った数)を追加。i18n は日英両方追加済み。

## Task 3: 動作確認

環境: 実データを汚さないよう `KNOWLEDGE_DATA_DIR` をコピーに向けて実行。
本番(8092)への反映は、別機能の作業と並行のため**未実施**(ユーザー指示による)。

### 3-1. rogue AP の重複ケースの再現(修正前 → 修正後)

重複候補を実際に生んだ手動調査(「rogue AP のアラートが出てるんですが、何から見ればいいですか」)を、
承認済み 24 件だけを残した状態(= その調査が走った当時の状態)で再抽出した。

```
[knowledge] 承認済みと同じ知見のため見送り(llm):
  "Rogue APアラートの切り分けは、検知SSID名の照合とRSSI強度の確認か"
  → "Mistのrogue_apクリティカルアラートは正規SSID一覧との照合とRSS"
[knowledge] 候補を 0 件作成: origin=manual / 承認済みと同一で見送り 1 件
→ {"status":"empty","created":[],"duplicateApproved":1,"reasonCode":"allDuplicates"}
```

相手の承認済みエントリを検証:
- 本文(title / symptom / rootCause / action)が変わっていないこと: **true**
- 出典: 1 件 → 2 件(今回の runId が追加された)

**修正前はこの調査が pending に 1 件積んでいた。修正後は 0 件で、既存エントリの再確認として記録される。**

### 3-2. 未承認 52 件の一括判定(過剰検出の確認)

全 52 件を判定した結果: **duplicate 22 / related 18 / new 12**(LLM 呼び出し 6 回 / 501 秒)。

`new` 12 件には、以下のように既存と無関係な知見が正しく残った(握り潰されていない):

- 特定 AP へのクライアント集中による Airtime 競合
- SSID を分けても VLAN が同一だと論理分離できない
- AP 再起動 reason が COLD_HW_RESET の場合は電源系統障害を優先確認
- GW 復旧直後のサイト間 VPN tunnel_down の二次障害
- オフラインの AP はファームウェア配信が適用されず旧版のまま残る

うち 6 件は **LLM を呼ばずに** `new` と判定された(絞り込みで相手が 1 件も残らなかった)。
絞り込みが安全側に効いていることの確認になる。

### 3-3. 過剰検出を 1 件見つけて修正した

初回の 52 件判定で、以下を誤って `duplicate` と判定していた:

```
候補  : Config Out of Sync Criticalアラートは設定の実機未反映を示す
        対処 = 「Config Out of Sync 詳細を確認し、手動で再同期(Sync/Push)する」
承認済: Centralのサイトヘルスサマリーとアラート一覧の集計が食い違うことがある
        対処 = 「サマリーの数値だけで判断せず、アラート一覧を個別に確認する」
```

承認済みの方は Config Out of Sync を **例として挙げているだけ**で、知見そのものは
「サマリーとアラート一覧の食い違い」。対処も別の操作を指している。

プロンプトに次の 2 つの禁止条件を足して修正した:

1. 候補の「対処」が既存の「対処」と**別の操作**を指しているなら duplicate にしない
2. 既存が**例として名前を挙げているだけ**の事象について、候補がその事象自体の
   原因・対処を述べているなら duplicate にしない

修正後、この 2 件はいずれも `related` に変わることを再実行で確認。
同時に rogue AP 10 件の再判定では duplicate が 5 → 6 件に増え、
**再現率を落とさずに誤検出だけを潰せた**ことを確認した。

### 3-4. API / UI の動作確認(dev サーバ、ポート 8123)

- `POST /dedupe-pending`(検出): 4 件を判定 → duplicate 2 件を返す。
  返ってきた一致度は 0.26 / 0.16 で、**いずれも 46 のしきい値 0.35 未満**
  (= 46 では絶対に検出できなかった組)。うち 1 件は英語候補 → 和文エントリ。
- `POST /dedupe-pending`(`pairs` で統合): applied 2、pending 52 → 50、merged 1 → 3。
  相手の本文は不変、出典 1 → 2、mergedFrom 0 → 1、候補は `merged` + `mergedInto` 付きで残存。
- UI(ブラウザで実操作):
  - 未承認タブに「承認済みとの重複を検出」ボタンが出る。英語表示では
    "Find duplicates of approved" になる(日英とも辞書経由)。
  - 押すと「承認済みと同じ知見の候補 50 件中 18 件」のパネルが開き、
    「候補 → 相手」の組が一覧で出る。この時点ではデータは変わらない。
  - 「18 件をまとめて統合」を押すと 未承認 50 → 32 / 却下・統合済み 5 → 23、
    タブのバッジも 32 に追従。
  - 統合後も、残った候補には従来どおりマージ提案(「これは既存のナレッジと同じ可能性が
    あります」/ 一致度 0.38 / 「この既存にマージする」)が出ており、
    46 のマージ提案フローは壊れていない。

## 未確認・次回に持ち越し

- **本番(8092)への反映は未実施。** 別機能の作業と並行のため、両方揃ってから
  Docker rebuild する(ユーザー指示)。
- **実際の pending 50 件に対する統合はまだ適用していない。** 動作確認は
  コピーしたデータに対してのみ行っており、`data/knowledge/entries.json` は
  **未変更**(本番反映後に画面から実行する想定)。
- **LLM 判定には実行ごとのブレがある。** 同じ rogue AP 10 件で
  duplicate 5 件 → 6 件と揺れ、境界の候補(「rogue APアラート発生時の切り分け手順」)が
  duplicate と related の間で入れ替わった。安全側(related)に倒れると重複が残るだけなので
  実害は小さいが、「毎回同じ結果になる」ことは保証できない。
- **抽出時に duplicate と判定された候補の本文はどこにも残らない。** 出典が既存エントリに
  足されるので調査へは辿れるが、候補として何が書かれていたかは失われる
  (サーバログには出る)。誤判定が起きた場合に取り返しがつかない唯一の経路。
  気になるなら `KNOWLEDGE_DEDUPE_SUPPRESS=0` で候補を作る挙動に戻せる。
- **一括検出は 50 件で約 8 分かかる**(LLM 6 回)。画面は「検出中…」を出すだけで
  進捗は見えない。件数が増えると体感が悪くなる。
- **`score()` 自体は 46 のまま変えていない。** マージ提案(`similar`)と 47 の注入は
  従来の計算のままなので、そちらの挙動には影響しない。
- 最終的な `npm run typecheck` / `npm run build` はいずれもエラーなしで通っている。
