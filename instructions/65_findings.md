## 2. 関連度しきい値 — 実測と確定値(65 の中心的な作業)

### 2-1. ナレッジ層: 0.15(64 の仮説どおりの手順で測れた)

承認済みナレッジ **24 件**(64 番の時点では 8 件。その後増えた)に対し、
**サイト指定なしの junior 風の質問**を投げて `retrieve.ts` の `relevance()` の分布を見た。

| 質問の種類 | 最高スコア |
|---|---|
| ネットワークと無関係(有給申請 / 経費精算 / ランチ / プリンタ) | **0.079** ← ノイズ床 |
| 関連する質問 7 問 | 0.16 〜 0.63 |

しきい値ごとの「1 件以上拾えた関連質問の数」:

| thr | 関連 7 問中 | 無関係 4 問中 |
|---:|---:|---:|
| 0.10 | 6 | 0 |
| **0.15** | **6** | **0** |
| 0.18 | 3 | 0 |
| 0.30(既存の注入と同じ値) | 3 | 0 |

**0.15〜0.18 の間に崖がある。** 0.15 より下げても拾える数は増えず(0.10 でも 6)、
1 質問あたりの件数だけが増える(0.15 で 0〜5 件 / 0.10 で最大 9 件)。
ノイズ床 0.079 の約 2 倍で、崖の手前。→ **0.15 を採用**(上限 3 件)。

既存の注入(`retrieve.ts`)が 0.30 なのは、64 §1-5(e) の読みどおり
**サイト一致ボーナス 0.20 が乗る前提**で「内容が当たって初めて注入される」性質を作るため。
Coach は原則サイトを指定しないのでその加点が発火せず、同じ 0.30 では 7 問中 3 問しか拾えない。

### 2-2. 履歴層: 同じ式・同じ値では**破綻した**(64 の想定が外れた点)

64 §1-5 は 3 層を 1 つのしきい値で扱う前提で書いてあったが、実装して測ると破綻した。

最初の実装(重なり係数 / クエリ 0.7 + 回答 0.3 / しきい値 0.15)で
`GET /api/coach/materials` を叩いたところ:

```
質問: 「有給休暇の申請方法を教えてください」
  → 履歴 3 件が 0.194 で採用された(ネットワークと一切関係ない質問なのに)
```

原因は**しきい値ではなく式**にあった:

1. 重なり係数の分母は `min(|A|,|B|)` なので、**短い質問の bigram が
   1200 文字の回答本文のどこかに散らばって当たるだけで高く出る**。
2. 日本語の定型部分(「〜を教えてください」「確認すべき点を」)が共通で当たる。

ナレッジ層でこれが起きなかったのは、タイトル・症状が質問と同じくらい短いため。
**同じ式が層をまたいで通用しない**、というのがここでの実測上の発見。

実測(教材適格な履歴 152 件):

| 式 | 関連 5 問 | 無関係 5 問 | 近い外れ 2 問 |
|---|---:|---:|---:|
| 重なり係数(クエリのみ)@0.25 | 5 | **2** | 1 |
| 重なり係数(クエリ+回答)@0.35 | 4 | **1** | 0 |
| Dice(クエリのみ)@0.15 | 4 | **1** | 0 |

**どのしきい値を選んでも、無関係な質問か関連する質問のどちらかを必ず落とす。**
= 数値の調整では解けない問題だった。

### 2-3. 対処: 話題キーの一致を必須の門にする

質問と履歴の両方から**話題キー**(承認済みナレッジのタグ語彙 + ルール ID + 和文同義語表)を
機械的に抜き、**1 つも共有しない履歴は候補にしない**。順位付けだけを Dice 係数で行う。

| | 関連 5 問 | 無関係 5 問 | 近い外れ 2 問 |
|---|---:|---:|---:|
| 門あり + Dice @0.05 | **5** | **0** | **0** |

門が実質的な判別をしているので、しきい値 0.05 は「取りこぼしを防ぐ床」でしかない。
→ **履歴層 = 話題キーの門(必須)+ Dice(クエリ 0.8 / 回答 0.2)>= 0.05、上限 3 件。**

※ 話題キーの抽出は**ユーザーの入力**を機械的に見るだけで、
   CLAUDE.md が禁じる「**モデル出力**の自然文パース」には当たらない。

### 2-4. 副産物: ナレッジ層の和文の弱点も同じ門で消えた

`retrieve.ts` は冒頭で「和文はタグが英語で当たりにくい」と自認している
(実際「ローミングがうまくいかない」は Roaming SLE のエントリに 0.054 しか出ない)。
調査タブはサイト選択という別の手掛かりを持つが、Coach は質問文しか持っていない。

そこで**同じ話題キーが一致したら +0.15 する**加点をナレッジ層にも入れた。
無関係な質問では話題キーが 0 個になるため加点は発火せず、ノイズ床は変わらない。

| 質問 | 加点前 | 加点後 |
|---|---:|---:|
| ローミングがうまくいかないと言われました | 0 件 | **3 件**(0.206 / 0.225 / 0.150) |
| スイッチが落ちたって連絡が来たんですが | 0 件 | **3 件**(0.246〜0.262) |
| 有給休暇の申請方法 / ランチ / 経費精算 / プリンタ | 0 件 | **0 件**(変わらず) |

`retrieve.ts` 本体には手を入れていない(調査タブの挙動は 47 番のまま)。

## 3. hintLevel と 3 ターン規則 — 実データでの確認

同一セッションで rogue AP の話題を 3 往復した実測:

| ターン | 学習者の発話(要約) | hintLevel | 往復 | 強制開示 | Coach の応答の性質 |
|---:|---|---:|---:|:---:|---|
| 1 | アラートが出てると言われた、何から見れば | **0** | 1/3 | — | 問い返しのみ(「今どこまで確かめた?」) |
| 2 | 不正な AP だと思うんですが… | **1** | 2/3 | — | 観点を 1 つだけ提示し、最後に 1 問 |
| 3 | やっぱり分からない、近くの他社の AP かも | **3** | 3/3 | **○** | **答えを開示** + 「次に同じ症状を見たら最初にどこを見る?」 |

- **0 → 1 → 3 と、設計どおり 3 ターン目で強制的に開示へ飛んだ。**
- hintLevel 3 のターンでだけ、素材の「答えにあたる部分」(rootCause / action、
  履歴の 2 手目以降)がプロンプトに載る。**2 以下では渡していない**
  (「載せるが言うな」だと必ず漏れるため)。
- 開示ターンの末尾に retrieval practice の問いが実際に入った(プロンプトの指示どおり)。

その他 3 経路の確認:

| 経路 | 結果 |
|---|---|
| 🔓 もう答えを教えて(escalate) | 2 ターン目で hintLevel 0 → **3**、`escalated:true` を記録 |
| 障害対応中モード | 1 ターン目から hintLevel **3**。「まず即答」の応答になった |
| 一般論のみ(うちの記録に無い) | `generalOnly:true` が立ち、画面に「一般的な推奨から説明するね」を表示 |
| 教材ゼロ | 「うちの記録には該当が無い」と正直に言い、状況を具体化する問いを 1 つ返した |
| 英語(lang=en) | 地の文が英語に切り替わり、hintLevel の挙動は同じ |

所要時間は **6〜8 秒**(MCP なし)。64 §2-1(b) の見立て(調査 1 回は 113 秒で対話に使えない)
に対し、対話として成立する範囲に収まった。タイムアウトは 90 秒に設定。

**実装上の判断(64 に無かった点):** 失敗したターンでは hintLevel と往復数を進めない。
学習者は何も受け取っていないのに状態だけ進むと、再送 3 回で答えに飛んでしまうため。

## 5. マーカー方式の遵守 — **画面確認で 1 件バグが出た**

| マーカー | 用途 | 実測 |
|---|---|---|
| `[SRC:knowledge:<id>]` 等 | 出典宣言 | 壁打ち・クイズとも出力を確認。**渡した素材の id 集合に含まれるものだけ採用**(捏造対策)。本文からは除去済み |
| `[LEVEL:L1\|L2\|L3]` | 理解段階の見立て | 出力を確認(L1 → L1 → L3 と推移)。次ターンの入力に反映 |
| `[VERDICT:correct\|partial\|wrong]` | 正誤判定 | 出力を確認。**出なかった場合は `partial` に倒す**(correct に倒すと誤答を正解扱い、wrong に倒すと正答を否定するため) |

30 番で「モデルが `[SKIP]` を出さずに無言省略する」実績があったので、
マーカー規則を **【最重要】として system prompt の独立ブロック**にし、
翻訳・全角化・言い換えの禁止を明記した。無言省略は今回の範囲では起きていない。

### 5-1. 発見したバグ: `[LEVEL:L0]` が本文に漏れた

本番画面で壁打ちしたところ、Coach の吹き出しの末尾に **`[LEVEL:L0]` がそのまま表示された。**

原因: 検出用と除去用で**同じ**正規表現(`L1|L2|L3`)を使っていた。
プロンプトは L1〜L3 しか指示していないが、モデルは**仕様に無い `L0`** を出してきた。
すると `L1|L2|L3` にマッチしないので検出もされず、**除去もされず**、そのまま画面に出た。

一般化すると:

> **マーカー方式では「検出できないもの = 除去できないもの」になり、
> 想定外の値がそのままユーザーに見える。**
> 30 番の教訓(無言省略)は「マーカーが**出ない**」ケースだったが、
> これは「マーカーが**想定外の形で出る**」ケースで、失敗の出方が逆。

対処: **除去は検出より必ず広く取る**(`markers.ts` に方針としてコメントを残した)。

| | 正規表現 | 方針 |
|---|---|---|
| 検出 | `\[LEVEL:(L[123])\]` 等 | **厳密。** 想定外の値は「宣言なし」として扱う(誤った値で内部判定を動かさない) |
| 除去 | `\[(?:SRC\|LEVEL\|VERDICT):[^\]\n]{0,160}\]` | **緩い。** 値の中身は問わず、マーカーの形をしたものは全部落とす |

検証(`stripMarkers` / `detect*` に 6 ケース):
実際に出た `[LEVEL:L0]`、`[VERDICT:CORRECT]`(大文字)、`[VERDICT:almost]`(仕様外)、
箇条書き記号付きの行、文中への混入、マーカーなし — **すべて漏れなし・検出は厳密のまま。**

あわせてプロンプト側にも「**この 3 つ以外を書かない。L0 や L4 は存在しない**」の一文を
日英とも足した(モデル側の予防と、パーサ側の防御の二重にする)。

## 7. クイズ・弱点・根拠リンク

### クイズ
出題 → 解答 → フィードバックの 1 周を実測(形式 `cause` / 難易度 ★★☆):

| 往復 | 解答(わざと浅く) | verdict | 開示 |
|---:|---|---|:---:|
| 1/2 | 「とりあえず AP の状態を見ます」 | `wrong` | — |
| 2/2 | 「アラートの一覧を見てみます」 | `partial` | **○**(上限に達したので必ず解説) |

- 1 往復目は**「そう考えた理由は?」から入り**、誤概念の特定を試みた(設計どおり)。
- 2 往復目で解説に到達し、末尾に retrieval practice の問いが入った。
- 素材の重複回避は `material-usage.json` の「未出題 → reviewAfter 経過 → 古い順」。
  間隔反復も入れた(correct 30 日 / partial 10 日 / **wrong 3 日で戻す**)。

出題プールは実測で **承認済みナレッジ 24 + 教材適格な履歴 152 + ルール 29**。
64 §3-1(f) が心配していた「ナレッジ 8 件では 3 日で尽きる」問題は、
ナレッジが 24 件に増えたことと履歴 152 件が主力になることで当面は解消している。

### 弱点
学習者 ID は持たない(デモ用途のため認証機構を作らないという確定事項)。
話題キーごとに 1 つのプロファイルへ集約し、誰でも見られる形で表示する。

実測で `switch-offline`(平均ヒント 2.0 / 答えを見た 1 回)、`ap-offline`(平均ヒント 1.33)等が
蓄積された。反映先も設計どおり実装:

- 弱点タグでは hintLevel を **1 から**開始(苦手なところで空振りさせない)
- 弱点タグでは 3 ターン規則を **2 ターン**に短縮
- クイズの素材選択で弱点タグを **1/3 の確率で**優先(常にではない。弱点ばかりだと続かない)
- **`attempts` / 壁打ち回数が 3 に届くまで「苦手」と呼ばない。** 届かないものは
  「まだ様子見中」として別に並べる

### 根拠リンク(ネタバレの制御)
64 §5-3(c) の「時間軸で分ける」をそのまま実装:

- hintLevel 0〜2 … 「🔒 元にした記録が N 件あるよ。答え合わせのあとで開けるようにしてある」
  **タイトルも畳んだまま**
- hintLevel 3 / クイズ解説後 … 全部展開可能。モデルが `[SRC:]` で挙げたものに「使った」バッジ

## 8. 本番反映 — 標準手順が使えず、迂回した(重要な申し送り)

### 8-1. 起きたこと

`docker compose up -d --build` が **`[internal] load metadata for docker.io/library/node:22-slim`
で 16 分以上止まった**(その後も進まず、中断)。切り分け結果:

| 確認 | 結果 |
|---|---|
| ホストのシェルから Docker Hub | **到達する**(`registry-1.docker.io/v2/` が 0.6 秒で 401 = 正常応答) |
| Docker daemon から Docker Hub(`docker pull node:22-slim`) | **1 行も出力せず無反応**(2 分以上) |
| ビルドキャッシュの使用状況 | 直近数分の使用実績なし = 進んでいない |

→ **Docker Desktop の daemon 側だけが Docker Hub に到達できない状態。**
`node:22-slim` はローカルにタグとして残っておらず(ビルドキャッシュ内にのみ存在)、
buildkit がタグ → digest の解決で必ず registry に問い合わせるため、ここで止まる。
**65 番の変更とは無関係の環境要因。**

### 8-2. 迂回した方法

Docker Desktop の再起動は他プロジェクトのコンテナ(6 個稼働中)を巻き込むので行わず、
**registry に一切問い合わせないビルド**に切り替えた:

```
FROM multi-network-dashboard-app:latest   ← 2 日前のビルドで作られた既存イメージ
COPY tsconfig.json vite.config.ts index.html src public server plugins ...
RUN npm run build && mkdir -p /app/data/coach && chown -R node:node /app
```

`docker build --pull=false -f ... -t multi-network-dashboard-app:latest .`
→ `docker compose up -d --no-build`

土台(node:22-slim / apt / claude CLI / `npm install`)は**前回のビルドで作られた層そのもの**なので、
中身は `docker compose up -d --build` が作るイメージと実質同じ。差分はソースと `npm run build` だけ。

### 8-3. 申し送り

- **daemon の Docker Hub 到達性が戻ったら、一度 `docker compose up -d --build` を通しておくこと。**
  現行イメージは既存イメージの上に積んだものなので、base image の更新が当たっていない。
  `Dockerfile` 側にも `data/coach` 等の mkdir を追加済みなので、通常ビルドでそのまま通る。
- 迂回用の Dockerfile は `/tmp/mnd-nopull.Dockerfile`(一時ファイル。リポジトリには入れていない)。

### 8-4. 反映後の確認(ポート 8092)

`server/index.ts` への追加は、ナレッジ・ベストプラクティスの初期化より**後**に置いた
(Coach が両者の読み取りに依存するため)。起動ログ・`GET /api/coach/status` とも正常。
§3 / §6 / §7 の画面確認はすべて**本番コンテナ(8092)に対して**実施した。
