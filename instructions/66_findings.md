# 66_findings — Coach の画面操作混同バグの修正

対象: `plugins/coach/`(65 番で実装した Coach タブ)
方針: ヒント・質問は「機器と現象に着目した一般的なチェック観点」に留める。
Central / Mist の具体的な知見は今までどおり使ってよい。禁止するのは
**Multi Network Dashboard(このアプリ)自身の UI 操作への言及だけ**。

---

## 1. 原因調査(Task 1)

### 1-1. 発生源は教材ではなく **system prompt 自身**だった

`plugins/coach/prompt.ts` の【絶対規則】が、Coach に自アプリのタブ名を
名指しで案内させていた。

| 箇所 | 修正前の記述 |
| --- | --- |
| prompt.ts:91(ja) | 「今の状態を聞かれたら**「ネットワーク調査タブで実際に見てみよう」と促す**」 |
| prompt.ts:154(en) | 「…point them to the **Network Investigation tab** to look for themselves.」 |
| prompt.ts:37(ja) | `L1 = 用語が分からない → 用語の意味と**「どの画面のどこを見るか」**から教える` |
| prompt.ts:41(en) | `L1 = … teach the term and **WHERE to look (which screen, which field)**` |

前 2 者はタブ名の直接の供給源。後 2 者(LEVEL_GUIDE)は
「初学者には画面の場所から教えろ」というトーン設定で、
**画面ベースの回答を全体的に後押ししていた**。

報告された「ネットワーク調査タブを開いて」は、教材由来ではなく
この 91 行目がそのまま出てきたものだった。

### 1-2. 教材ソースは汚染されていなかった(疑いは否定)

「調査履歴に画面名が混入していて、それが教材として使われている」という
当初の疑いは、実データを走査した結果 **否定された**。

| 教材ソース | 走査対象 | 自アプリ UI 名称の混入 |
| --- | --- | --- |
| 調査履歴 | `data/network-investigation/query-history.jsonl`(216 行) | **0 件** |
| ナレッジ | `data/knowledge/entries.json`(76 件 / 承認済み 24) | **0 件** |
| ベストプラクティス | `src/i18n/{ja,en}.json` の `bestPractice.rules.*.title / .desc` | **0 件** |

走査パターン: `ネットワーク調査タブ` / `調査タブ` / `ナレッジタブ` /
`ベストプラクティスタブ` / `Multi Network Dashboard` / `このダッシュボード` /
`本ダッシュボード` / `Network Investigation tab`。

辞書全体では 22 箇所が `ネットワーク調査タブ` を含むが、いずれも
**他タブの UI 文言(ボタンの title 属性・ヒント)**で、
`materials.ts` の `ruleText()` が読む `bestPractice.rules.*` 配下には 1 件も無い。
教材ブロックにこれらが載る経路は存在しない。

### 1-3. Coach の実行ログでの再現(修正前)

`data/coach/sessions.jsonl` の回答を重複除去すると 25 件。
そのうち **11 件(44%)** が自アプリの UI に言及していた。

| 一致した表現 | 件数 | 出どころ |
| --- | --- | --- |
| `Multi Network Dashboard` | 8 | 学習者が名前を出した後、Coach が拾って会話を続けた |
| `ネットワーク調査タブ` | 3 | **学習者が一度も言っていない**。prompt.ts:91 由来 |
| `Network Investigation tab` | 1 | 同上(prompt.ts:154 由来) |

`ネットワーク調査タブ` は学習者の発言に一度も現れないまま Coach 側から出ている。
これが 1-1 の結論の裏付けになる。

## 2. 修正内容(Task 2)

### 2-1. 予防: system prompt(`plugins/coach/prompt.ts`)

- **新設**: `APP_UI_RULES`(ja / en)= 【このアプリの画面には触れない(最重要級)】
  - 自アプリの画面・タブ・ボタン・メニューの操作を回答やヒントに含めない
  - アプリ名そのものを書かない / **相手がアプリ名を出しても画面の中身を推測しない**
  - ヒントは常に「機器と現象に着目した一般的なチェック観点」で書く
    - 良い例:「そのスイッチ自体のステータスは確認した?」「上流(アップリンク)の機器は生きてる?」
    - 悪い例:「ネットワーク調査タブを開いて」「ダッシュボードの一覧を見て」
  - **Central / Mist の具体的な話は制限しない**ことを明記
    (設定項目名・SLE 名・実際に叩いた API / ツール名は具体的に挙げてよい)
- 挿入先は **4 つの prompt すべて**:
  壁打ち(`buildChatSystemPrompt`)/ 出題(`buildQuizGenSystemPrompt`)/
  採点(`buildQuizGradeSystemPrompt`)。ja / en の両方。
- prompt.ts:91 / :154 を書き換え。「タブを案内する」→
  「実際の管理画面で今の値を確認しよう + **何を確認すべきか**を 1 つ示す」。
- LEVEL_GUIDE の L1 を書き換え。「どの画面のどこを見るか」→
  「その値が**どの機器・どの管理システムのどんな項目**として現れるか」。
- 出題 prompt では、規則を後ろに足したことで直前の出力形式指示が弱まり
  「〜な問題を作ります」という前置きが付く実測があったため、
  末尾に形式の念押しを 1 行入れた(4-4 参照)。

### 2-2. 検出: `plugins/coach/app-ui.ts`(新規)

**プロンプト指示だけでは足りない**と判断した。根拠:
学習者が「Multi Network Dashboard」と入力したターンでは、
モデルがその語を引用し返す形で違反が再発した(4-3 の 1 回目の下書き)。
30 番で「モデルが指示どおりのマーカーを無言で省略する」実績もある。

一方で **本文の機械的な書き換えはしない**。文の途中を削ると日本語として壊れる。
言い直しはモデルにさせる。

- `detectAppUiMentions(text)` — 3 つの規則で機械的に検査する
  - `appName` … `Multi Network Dashboard` / `マルチネットワークダッシュボード`
  - `selfRef` … 「この/本/当/その + ダッシュボード/アプリ/ツール」、英語は `this app|application|dashboard|tool`
  - `tab` … 自タブ名(ネットワーク調査 / グローバル概要 / ナレッジ / ベストプラクティス …)
    **+ 面(タブ / 画面 / ページ / tab / screen …)**の組。
    タブ名だけでは弾かない(「ナレッジ」「ベストプラクティス」は普通名詞としても使うため)
- **ベンダー語による見逃し**: 一致箇所の直前 24 文字に
  `central|mist|aruba|juniper|hpe|marvis|clearpass` があれば見逃す。
  「Central のレポート画面」「Mist の Insights ページ」は正当な具体的言及であり、
  66 番で禁止したいものではない(= 禁止しすぎの防止)。
  アプリ名だけはこの見逃しを適用しない(「Central の Multi Network Dashboard」は成立しないため)。
- `runGuarded()` — 生成 → 検査 → **1 回だけ**言い直し
  - 言い直しの指示には「Central / Mist の具体は今までどおり書いてよい」
    「**書き直した経緯には触れない**(前置きを書かない)」
    「相手がアプリ名を出しても引用し返さない」を含める
  - 言い直しが実行エラーなら 1 回目を採用(体裁の問題で回答そのものを失わせない)
  - 2 回やっても落ちなければ言い直し版を採用してログに残す(回答が返らないより良い)
  - `durationMs` は 2 回ぶんの合算(遅くなった理由が見えるように)

> CLAUDE.md 第 3 項との関係: これは**モデル出力の自然文パースではない**。
> 意味を読み取って分岐しているのではなく固有名詞の混入を機械検査しているだけで、
> 判定結果は「もう一度書かせるか否か」にしか使わない。

## 4. 動作確認(Task 3)

| シナリオ | ターン | 結果 |

| **スイッチ障害(添付の質問例)** 「スイッチが落ちたって連絡が来たとき、最初に何を確かめますか」 | 3 | 自アプリ UI **0 件**。ガード発火なし |

出てきたヒントの形(いずれも 1 回目の生成、言い直し無し):

### 4-2. Central / Mist の具体的な言及(禁止しすぎの確認)

「Aruba Central でスイッチのオフラインを調べるとき、どのツールや画面を見るのが定石ですか。
**具体的な名前で教えてください**」と、あえて具体名を要求した。

- Coach は Central のデバイス一覧のステータス列(Online / Offline)、
  ヘルススコアやアラート件数を鵜呑みにしない理由、
  Mist 側の調査の型(自組織・サイトの特定 → 該当イベントの検索 → 現在の統計 → インサイト)、
  Roaming SLE の分類器(fast-roam / 11r / OKC の失敗件数)などを**具体名で回答した**
- ガードは **1 件も発火しなかった**(ベンダー語の見逃しが効いている)

→ **禁止が過剰になっていないことを確認**。

## 5. 検証中に見つかった、**66 番では直していない**既存の挙動

いずれも 65 番からある挙動で、今回の変更が原因ではない。

- **(a) エスカレーション時に教材が空になることがある。**
  `api.ts` の検索文は「今回の発言」なので、「もう答えを教えてください」だけを送ると
  その文字列で教材を引きに行き、0 件になる。結果 `hintLevel=3` なのに
  「うちの記録には無い」と返り、**開示の保証が空振りする**。
  直前ターンの話題キー / 質問文を検索文に混ぜるのが筋。

- **(b) 短い相槌で話題キーが誤検出され、往復数がリセットされる。**
  「うーん、思いつかない」で `topic=[pmf,methodology]` が立ち、
  `turnsOnTopic` が 1 に戻った(3 ターン規則が遠のく)。
  `extractTopicKeys()` が素材のタグにフォールバックすることによる。

- **(c) 英語の回答で学習者を三人称で書くことがある。**
  「They should not need to open anything」。ja では観測していない。

- **(d) 出題文に前置きが付くことがあった。**
  4-4 の念押し追加後は 4 回とも再現せず。モデル差の可能性もあるため、
  再発したら出題 prompt の末尾の形式指示を疑うこと。
